# Задача 5: доказательства починки приборов (Н-12, М-17, М-18)

Каждый раздел — пара «до» и «после», как требует правило задачи. Полный повторный
прогон `tools/measure-trigger.ps1` (11 формулировок × 2 среды × 2 среза = 44 прогона,
часы фонового времени при ~7 минутах на прогон Claude Code) не проводился — задача 5
прямо разрешает это при условии обоснования (см. `.superpowers/sdd/2026-08-23-core-remediation/task-5-brief.md`,
пункт 4): требуется показать, что прибор **способен** наказывать, а не переизмерить
description набора заново. Ниже — то, чем это показано: код и малая живая выборка.

## Н-12: прибор получил отрицательный член и способен наказывать

**До.** `tools/measure-trigger.ps1` (состояние до задачи 5) держал массив `$prompts`
из шести строк, все — из предметной области набора («Напиши запрос по остаткам…»,
«Сделай отчёт по продажам…»). Ни одной формулировки с ожиданием «навык подниматься
не должен» в массиве не было структурно — то есть посчитать ложное срабатывание
было нечем в принципе, независимо от того, что показал бы прогон. Это видно чтением
кода, без запуска: `$prompts = @('Напиши запрос…', …)` — плоский список строк,
никакого поля «ожидание».

**После.** `$prompts` — список объектов с полями `Text` и `Expect`; добавлено пять
отрицательных формулировок (SQL к MS SQL, PostgreSQL, Python, JavaScript, nginx —
подобраны по возражению рецензента: без двусмысленных «перенеси базу 1С на
PostgreSQL», это законная область `1c-build-and-db`). `Run-Stage` считает
`Верно = (Навык -eq Ожидание)`, итог — две величины на среду и срез: попадание на
своей области и ложные срабатывания на чужой.

Проверено дважды:

1. **Логика подсчёта** — прогон `tools/measure-trigger.ps1 -DryRun` (случайные
   `Навык`, без обращения к моделям) корректно разделил положительные и
   отрицательные формулировки и вывел обе величины раздельно для Kilo и Claude Code,
   например: «Kilo: срабатывание на своей области — было 3 из 6, стало 1 из 6.
   Ложные срабатывания на чужой области — было 4 из 5, стало 4 из 5.» — то есть
   вторая величина существует и меняется независимо от первой, чего раньше не было
   структурно.
2. **Живой сигнал на реальном (уже расширенном) description** —
   `tools/run-prompt.ps1` напрямую, без полного конвейера. Все строки ниже — журналы
   структурного детектора (Kilo: `--format json`, задача 5; Claude: `tool_use`
   "Skill", не менялся этой задачей):

   | Среда | Формулировка (отрицательная) | Навык | Журнал |
   |---|---|---|---|
   | kilo | Объясни синтаксис цикла for в Python. | False | `1c-run/4f12226a/run.log` |
   | kilo | Напиши SQL-запрос к MS SQL по таблице заказов. | False | `1c-run/51d116b2/run.log` |
   | kilo | Настрой резервное копирование PostgreSQL по расписанию. | False | `1c-run/fb0264e5/run.log` |
   | claude | Объясни синтаксис цикла for в Python. | False | `1c-run/7610c951/run.log` |

   Ноль ложных срабатываний на этой выборке — расширенное description (в SKILL.md
   на момент задачи 5) не наказывается, потому что не заслуживает наказания на этих
   формулировках. Это не «замер не смог найти брак», а «замер смог посчитать и
   насчитал ноль»: до задачи 5 эта строка отчёта не существовала бы вовсе.

   **Где эти журналы (M-7 финального ревью, долг назван 23.08.2026).** Колонка
   «Журнал» ссылается на `1c-run/<хэш>/run.log` — это `%TEMP%/1c-run/<хэш>/run.log`,
   каталог временный, в репозиторий он не идёт и идти не должен: это сырые
   стенограммы агента на 3–210 КБ каждая, с идентификаторами сеансов и путями
   машины разработчика. **Так и записываем — временные, а не приложенные.**

   Чтобы ссылка не осталась голой, решающий признак вынут из каждого журнала
   и записан здесь (перепроверено 23.08.2026 прямым поиском по тем же файлам,
   пока они ещё на месте):

   | Журнал | Среда | Признак в файле | Навык |
   |---|---|---|---|
   | `1c-run/4f12226a/run.log` | kilo | `"tool":"skill"` — 0 вхождений; событий инструментов нет вовсе | False |
   | `1c-run/51d116b2/run.log` | kilo | `"tool":"skill"` — 0; из инструментов только `bash` | False |
   | `1c-run/fb0264e5/run.log` | kilo | `"tool":"skill"` — 0; инструменты `bash, edit, read, todowrite, write` | False |
   | `1c-run/7610c951/run.log` | claude | `"name":"Skill"` — 0, `"type":"tool_use"` — 0 | False |
   | `1c-run/3e8ce091/run.log` | kilo | `"tool":"skill"` — **1**; инструменты `bash, glob, read, skill, write` | True (положительная формулировка, таблица ниже) |

   Воспроизвести любой из них заново:

   ```powershell
   powershell -NoProfile -File tools/run-prompt.ps1 -Env kilo -Prompt '<формулировка>'
   ```

   Прогон вернёт свой каталог и своё поле `Навык`; хэш будет другим —
   недетерминированность моделей записана в этом файле отдельно и не скрывается.

   **Поправка ревью.** Первый прогон Python и MS SQL на Kilo (журналы `53045057` и
   `e03232b3`) состоялся ДО правки `run-prompt.ps1` — это диагностировал рецензент
   по PowerShell-ошибке в самих журналах (`run-prompt.ps1:13 char:5`, команда без
   `--format json` — строка 13 версии `ecf6db8`, до правки; в текущей версии эта
   команда на строке 17 и уже с флагом). Оба результата случайно совпали с
   ожиданием, потому что старый подстрочный поиск по короткому нерелевантному
   ответу тоже не нашёл имени навыка — но заявление «проверено новым детектором»
   было неверным для этих двух строк. Обе формулировки перегнаны Kilo заново
   23.08.2026 после правки (`4f12226a`, `51d116b2`, таблица выше); оба журнала —
   настоящий `--format json`, оба разобраны построчно: у Python нет ни одного
   события `tool_use`, у MS SQL есть одно, `part.tool == "bash"` (не `"skill"`) —
   `Навык = False` в обоих случаях получен структурным признаком, не совпадением.

## М-17: детектор Д-11 в `tools/run-acceptance.ps1` ловил по имени сервера, а не по признаку

**До.** Регулярное выражение `"unknown MCP server 'skills'|read_mcp_resource|skills/read_mcp_resource"`
проверено против двух реальных сигнатур из `docs/evidence/2026-08-22-acceptance.md:124-125`:

```
OLD -> False   на "r1/list_mcp_resources … unknown MCP server 'r1'"
OLD -> False   на "resources/read failed for codex_apps (file:///.../SKILL.md)"
```

Обе реальные записи свидетельства детектор пропускал: имя сервера, зашитое в
регэксп (`'skills'`), не совпадало ни с `'r1'`, ни с `codex_apps`, а вариант
`list_mcp_resources` не совпадал с зашитым `read_mcp_resource` вовсе (другое
слово — `list`, не `read`).

**После.** `"(list|read)_mcp_resource|unknown MCP server|resources/read failed"` —
структурный признак без имени сервера:

```
NEW -> True    на "r1/list_mcp_resources … unknown MCP server 'r1'"
NEW -> True    на "resources/read failed for codex_apps (file:///.../SKILL.md)"
```

Проверено `-match` в PowerShell на тех же двух строках свидетельства.

Заодно закрыт второй дефект того же М-17: комментарий у `$CodexFailLimit` обещал
«подряд», но `$codexFails` нигде не обнулялся.

**До/после (симуляция последовательности неудача → удача → неудача, предел 2):**

```
OLD (без сброса): codexFails = 2 после третьего события → автомат сработал бы,
                   хотя неудачи не шли подряд
NEW (со сбросом): codexFails = 1 после третьего события → автомат не сработал,
                   что и обещает слово «подряд»
```

## М-18а: `measure-trigger.ps1` не ставил навыки перед стадией «до»

**До.** Порядок был: `$before = Run-Stage 'до'` → затем чтение `$oldDesc` из
`$SkillFile` → затем правка файла и переустановка. Стадия «до» измеряла то, что
было установлено ПРЕДЫДУЩИМ прогоном (возможно, устаревшее), а `$oldDesc` для
отчёта читался из репозитория уже после измерения — отчёт мог называть не ту
формулировку, которая реально стояла в момент измерения.

**После.** Установка (`install-skills.ps1`) вызывается перед стадией «до»; `$oldDesc`
читается из того же файла сразу после установки, и в файл прогресса пишется
SHA-256 обеих формулировок (`before-hash`, `after-hash`) — по нему видно, что именно
было установлено в момент каждого среза. Изменение — структурное (порядок вызовов
в скрипте), проверено чтением кода и прогоном `-DryRun` (события `install-before`,
`before-hash` появляются в файле прогресса раньше `run/stage=до`).

## М-18б: детектор Kilo был подстрочным поиском по всему журналу

**До.** `tools/run-prompt.ps1` запускал `kilo.exe run --auto --dir $Dir $Prompt` (без
`--format`, то есть человекочитаемый текст) и искал `$txt -match
'developing-1c-configurations|1c-build-and-db'` по всему журналу целиком —
засчитывалось любое упоминание имени, не только вызов. Это структурное свойство
кода, видно без запуска; ранее уже зафиксировано находкой №10 (`docs/plan.md`) как
«верхняя оценка, не факт вызова».

**После.** Обнаружено (проверено запуском 23.08.2026): `kilo.exe run --help`
называет `--format json` («raw JSON events»). Живой прогон с этим флагом даёт
структурные события, включая `{"type":"tool_use",...,"part":{"tool":"skill",
"state":{"input":{"name":"developing-1c-configurations"}}}}` — тот же класс сигнала,
что и `tool_use` "Skill" у Claude Code. `run-prompt.ps1` теперь для Kilo парсит эти
события и засчитывает `Навык = True` только при `type == 'tool_use'` и
`part.tool == 'skill'`, а не при любом текстовом упоминании.

Проверено живым запуском через `run-prompt.ps1` **после** правки — все четыре
журнала ниже содержат настоящий `--format json` (проверено разбором событий по
типам построчно, не только итоговым `Навык`):

| Формулировка | Ожидание | Навык (новый детектор) | Журнал | Структурная проверка |
|---|---|---|---|---|
| Добавь справочник Договоры. | должен подняться | **True** | `1c-run/3e8ce091/run.log` | событие `tool_use`, `part.tool=="skill"`, `name=="developing-1c-configurations"` |
| Объясни синтаксис цикла for в Python. | не должен | **False** | `1c-run/4f12226a/run.log` | ни одного события `tool_use` в журнале |
| Напиши SQL-запрос к MS SQL по таблице заказов. | не должен | **False** | `1c-run/51d116b2/run.log` | одно событие `tool_use`, `part.tool=="bash"` — не `"skill"` |
| Настрой резервное копирование PostgreSQL по расписанию. | не должен | **False** | `1c-run/fb0264e5/run.log` | событий `tool_use` со `skill` нет |

Структурный детектор верно различил вызов и невызов на всех четырёх пробах. Kilo
больше не даёт «верхнюю оценку» — оба детектора (Kilo и Claude Code) теперь одного
класса точности.

**Поправка ревью 23.08.2026.** Первая версия этого раздела включала журналы
`53045057` (Python) и `e03232b3` (MS SQL) с подписью «после правки» — неверно:
рецензент нашёл в них диагностику PowerShell `run-prompt.ps1:13 char:5` без
`--format json`, то есть строку 13 версии до правки (`git show ecf6db8:tools/
run-prompt.ps1`; в текущей версии эта команда на строке 17, уже с флагом). Оба
результата совпали с ожиданием случайно — старый подстрочный поиск по короткому
нерелевантному ответу тоже не нашёл имени навыка. Обе формулировки перегнаны
заново после правки (таблица выше, журналы `4f12226a` и `51d116b2`) — итог тот же
(`False`), но теперь получен структурным признаком, а не совпадением. Таблица
выше — окончательная, четыре из четырёх строк действительно проверены новым
детектором.
