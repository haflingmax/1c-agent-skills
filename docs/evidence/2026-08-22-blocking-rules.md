# Доказательство правил проверяльщика запуском (2026-08-22)

Платформа: `C:/Program Files/1cv8/8.3.27.2325/bin/1cv8.exe`.
База: `D:/1C/base/trade` (файловая, одноразовая).
Скрипт: `tools/prove-blocking-rules.ps1`.

## Перепрогон 2026-08-23 (задача 2)

Задача 2 пересобрала `cli-keys.json` целиком: у `/DumpResult` теперь два
режима вместо одного, добавлен `/@`, у 11 ключей вернулись 30 потерянных
опций. Ни один из этих трёх дефектов не завязан на 14 случаев ниже — они
проверяют `/DumpCfg`, `/LoadCfg`, `/Lru`, `/Publish` и режимный разрез, а не
`/DumpResult`, `/@` или урезанные `opts`. Поэтому перепрогон ожидаемо
подтвердил: столбец «Как теперь» не разошёлся ни в одной строке.

Разошёлся только контрольный размер файла: было 4973 байта, стало 75395.
Причина — база `D:/1C/base/trade` подросла между прогонами (она
одноразовая, её намеренно меняют другие задачи), а не код проверяльщика:
все восемь проходных случаев по-прежнему дают побайтно одинаковый файл, и
SHA256 `/DumpCfg` и `/DumpDBCfg` по-прежнему совпадают (см. ниже). Отдельная
находка процесса: перед перепрогоном пришлось снять зависший `1cv8.exe`
(PID держал файловую блокировку базы, осиротев от прежнего случая
«конфигуратор-в-enterprise», где платформа открывает сеанс и не завершается
сама) — без этого шага все восемь проходных случаев ошибочно показывали код 1
«Ошибка блокировки информационной базы». Это внешнее состояние окружения,
а не регресс правил.

Процесс ожидается явно и с таймаутом. Без ожидания `1cv8.exe` — оконное
приложение — возвращает управление мгновенно, ничего не создав, и это выглядит
как тихий отказ. Голый `-Wait` тоже не годится: один из проверяемых случаев
(пакетный ключ конфигуратора в режиме ENTERPRISE) не завершается никогда, и
незавершение как раз и есть его результат.

Проверка двусторонняя, как требует правило 11 архитектуры: показать, что
запрещаемое действительно не работает, **и** что разрешаемое действительно
работает.

Одного правила здесь нет и быть не может: «чужой инструмент не судится».
`ibcmd.exe` идёт с серверными компонентами, на этой машине его нет.

### Куда делась работа при выдуманном ключе

Источник: ручная проверка координатора задачи 5 (2026-08-22) в чистом каталоге —

```
1cv8 DESIGNER /F D:/1C/base/trade /DumpCfgToFile <путь>/target.cf /DisableStartupDialogs /Out ... /DumpResult ...

код: 0, DumpResult: 0
target.cf создан: False
в рабочем каталоге появился: ToFile, 4973 байта
```

Повторено при подготовке этого отчёта и ещё раз 22.08.2026 расширенным прогоном,
в изолированном рабочем каталоге (`Start-Process -WorkingDirectory`, без общих
файлов с чужими прогонами): обычный `/DumpCfg` в тот же каталог создаёт файл
размером 4973 байта — то же число, что и у `ToFile`. Совпадение размера с
независимым запуском исключает случайность.

Перепрогон 23.08.2026 (после пересборки каталога задачей 2) воспроизвёл ту же
картину на новом размере базы: `ToFile` — 75395 байт, обычный `/DumpCfg`
в тот же каталог — тоже 75395. Механизм не изменился, изменилась только
база.

Вывод: платформа разбирает `/DumpCfgToFile` как `/DumpCfg` с хвостом `ToFile`,
принятым за позиционный аргумент — имя файла. Конфигурация выгружается
по-настоящему, только не туда: в файл `ToFile` в текущем рабочем каталоге, а
путь, переданный командой, отбрасывается как лишний. Это не «команда ничего не
сделала» — это «команда сделала не туда».

### Выдуманный ключ, начинающийся со слитного

Двенадцать ключей приложения 7 принимают значение слитно (`/L`, `/P`, `/N`, `/O`,
`/WSA` и прочие). Из-за этого выдуманный ключ, начинающийся с любого из них,
разбирается проверяльщиком как законный слитный со значением. Запуск показывает,
почему запретить его нельзя, и почему пропустить молча — тоже:

- `/Lru` рядом с `/DumpCfg` — код 0, файл создан, 4973 байта. Законный слитный
  ключ работает, запрет остановил бы верное.
- `/Publish` рядом с `/DumpCfg` — код 0, файл создан, 4973 байта. Выдуманный ключ
  платформу не смутил: операция сделана, лишнее проглочено.
- `/LoadCfgFromFile` **вместо** операции — код 1, файла нет, в журнале
  «Файл не обнаружен `…\FromFile`». Здесь видно, что платформа разбирает его
  по-своему: не как `/L` со значением `oadCfgFromFile`, а как настоящий
  `/LoadCfg` с позиционным аргументом `FromFile` — тот же механизм, что у
  `/DumpCfgToFile`, только на этот раз он упёрся в несуществующий файл.

Отсюда решение (2026-08-22, до задачи 3): **предупреждение, а не запрет** —
для ОБОИХ случаев одинаково. `/Lru` и `/Padmin` от `/Publish` и
`/LoadCfgFromFile` тогда были механически неотличимы: `known_key` искал
совпадение только среди двенадцати slitных ключей, и `/LoadCfgFromFile`
резолвился в `/L` точно так же, как `/Publish` — оба через один и тот же
код без разницы в происхождении совпадения.

### Задача 3 (2026-08-23): Н-02 — тот же механизм, другое решение

Ревью (`docs/reviews/2026-08-23-core-review.md`, находка Н-02) указало на
то, что не было видно 2026-08-22: платформа берёт самое длинное совпадение
по префиксу среди **ВСЕХ** ключей каталога, а не только среди двенадцати
slitных. `known_key` пересобран под эту модель (совпадение ищется по всем
140+ ключам, `glued` больше не фильтрует кандидатов). Из-за этого
`/LoadCfgFromFile` теперь резолвится в `/LoadCfg` (**не** glued), а не в
`/L` (glued) — и это ровно та разница, которая позволяет отличить его от
`/Publish` механически: не по виду хвоста, а по тому, является ли
**резолвнутый** ключ glued.

Повторный запуск воспроизведения на 8.3.27.2325, 2026-08-23 (шаг 1 задачи 3,
изолированный рабочий каталог, `Start-Process -Wait`):

```

$a = @('DESIGNER','/F','D:\1C\base\trade','/LoadCfgFromFile',"$w\t.cf",
       '/DisableStartupDialogs','/Out',"$w\l.log",'/DumpResult',"$w\rc.txt")
Start-Process -FilePath $exe -ArgumentList $a -Wait -PassThru -NoNewWindow -WorkingDirectory $w
```

```
код: 1
l.log (163 байта), rc.txt (4 байта) — t.cf НЕ создан
журнал: Файл не обнаружен 'C:\Users\ashil\AppData\Local\Temp\n05\FromFile'.
        2(0x00000002): Не удается найти указанный файл.
```

Побайтно то же, что и в замере 2026-08-22 (тот же файл `FromFile`, тот же
код 1, файл-цель не создан) — механизм не изменился, изменилось только то,
что теперь код отличает этот случай от `/Publish`.

**Новое решение, раздельно по двум случаям, а не одно на оба:**

| Случай | Резолвится в | glued резолвнутого ключа | Что показал запуск | Решение |
|---|---|---|---|---|
| `/Lru`, `/Padmin`, `/Publish`, `/NewConfiguration`, `/OptimizeDatabase`, `/WSAuthentication` | `/L`, `/P`, `/P`, `/N`, `/O`, `/WSA` | да | принят, операция выполнена (или проглочен рядом с ней) | **предупреждает** — не отличить от легитимного `/Lru`, запрет остановил бы верное |
| `/LoadCfgFromFile`, `/DumpCfgToFile` | `/LoadCfg`, `/DumpCfg` | нет | код 1, файла нет **либо** файл создан не туда (тихая порча) | **блокирует** — доказанно неверно, правило 11 разрешает запрет, и теперь есть механический признак (glued резолвнутого ключа), чтобы не задеть `/Lru` |

Цена решения по-прежнему та же для glued-случая — предупреждение и на
законном `/Lru` — она принята сознательно и задачей 3 не менялась. Новое —
только то, что не-glued случай (`/LoadCfg`, `/DumpCfg`) теперь отделён и
блокируется, вместо того чтобы получать то же предупреждение, что и
`/Publish`.

## Ревью задачи 3 (2026-08-23): формула «самое длинное среди ВСЕХ» неверна

Повторное ревью нашло Critical: формула из раздела выше — «самое длинное
совпадение по префиксу среди ВСЕХ ключей каталога» — блокирует законный
`/PRoxy2024` (после `/N Admin`). `/Proxy` (раздел 7.3.2) длиннее `/P`, и по
буквальной формуле совпадение должно уйти в `/Proxy`, а хвост `2024` — в
позиционный аргумент несуществующего для `/Proxy` вида. Найдено ревью,
проверено рецензентом на живой платформе, воспроизведено координатором
самостоятельно.

Формула была неверна, а не находка Н-02 в целом: два наблюдения (`/LoadCfg`
побеждает короткий `/L`, но `/Proxy` не побеждает короткий `/P`, хотя оба
длиннее) не укладываются в одно правило «длиннее — побеждает». Настоящая
модель выведена шестью новыми живыми прогонами 2026-08-23 (плюс два
воспроизведения уже известных случаев) — не рассуждением, а измерением.

эту аналогию не подтвердила.

### Выведенная модель: `absorbs_glued_tail`

Не «длина», а **форма документированного аргумента** резолвнутого
кандидата решает, участвует ли он в совпадении:

| Кандидат | `glued` | `arg` (из cli-keys.json) | Участвует в совпадении? | Почему |
|---|---|---|---|---|
| `/LoadCfg`, `/DumpCfg`, `/Out` | нет | `<голое значение> [опционально...]` | да | хвост токена сам становится этим значением — платформа проверено принимает его (иногда рушится об него, иногда тихо портит результат) |
| `/L`, `/P`, `/N`, `/O` и восемь других | да | (не проверяется — glued решает всегда) | да | по определению берёт значение слитно |
| `/Proxy` | нет | `-PSrv <адрес> -PPort <порт> [...]` — первым делом ИМЕНОВАННЫЙ под-ключ | **нет** | глued-хвост не может подставиться на место `-PSrv`; платформа откатывается к короткому `/P` |
| `/NoProxy` | нет | `""` (пусто — ключ вовсе не берёт аргумента) | **нет** | хвосту некуда деться; платформа откатывается к короткому `/N` |

Правило (реализовано как `absorbs_glued_tail()` в `check-1c-cli.py`):
кандидат участвует в поиске самого длинного совпадения, если он `glued`,
**либо** его `arg` (после `strip()`) начинается с `<` — то есть первый
обязательный компонент документированного синтаксиса это «голое» значение,
а не именованный флаг и не пустая строка. Среди участвующих кандидатов —
самое длинное совпадение, как и раньше.

Дальше решение о блокировке не изменилось: попал в совпадение glued-ключ —
предупреждение (легитимное слитное значение, `/Lru`, `/PRoxy2024` теперь
тоже сюда); попал не-glued «голый»-arg ключ — блокировка (доказанный
запуском провал или тихая порча: `/LoadCfg`, `/DumpCfg`, `/Out`).

### Итог по обеим находкам рецензента

| Команда | Резолвится в | Решение | Проверено запуском |
|---|---|---|---|
| `/PRoxy2024` (после `/N Admin`) | `/P` | **предупреждает** (новая блокировка законного устранена) | да, №1/№2 выше |
| `/OutBase` | `/Out` | **блокирует** (тот же механизм, что и `/DumpCfgToFile` — не новая блокировка законного, а корректное расширение уже принятого решения) | да, №3/№3b выше |

## Вывод по каждому правилу

Правило имеет право блокировать (`[ошибка]`, код 1), только если запуск показал,
что платформа заявленного не делает. Всё прочее — `[внимание]` с кодом 0.

| Правило проверяльщика | Что показал запуск | Как теперь |
|---|---|---|
| ключа нет в приложении 7 (`/DumpCfgToFile`) | отчёты об успехе, файла по указанному пути нет | блокирует |
| не указан режим запуска | код 1, «Неопределен режим запуска», ничего не создано | блокирует |
| не задана база | код 1, «Неопределена информационная база», ничего не создано | блокирует |
| заглушка вместо пути | код 1, «Неправильный путь к файлу», ничего не создано | блокирует |
| пакетный ключ конфигуратора вне DESIGNER | не завершился за 60 с, журнал пуст, `/DumpResult` не создан | блокирует |
| ключ чужого режима внутри DESIGNER | принят, выгрузка сделана, размер тот же | **предупреждает** |
| опция не от этого ключа | принята, выгрузка сделана, размер тот же | **предупреждает** |
| выдуманный ключ, резолвнутый в glued (`/Publish` → `/P`) | рядом с операцией — принят, выгрузка сделана, лишнее проглочено | **предупреждает** |
| выдуманный ключ, резолвнутый НЕ в glued (`/DumpCfgToFile` → `/DumpCfg`, `/LoadCfgFromFile` → `/LoadCfg`) — Н-02, задача 3 | вместо операции: код 1, файла нет («Файл не обнаружен»); либо файл создан не туда (тихая порча) | **блокирует** |
| законный слитный ключ (`/Lru`) | принят, выгрузка сделана, размер тот же | **предупреждает** (цена решения) |
| регистр ключа | `/dumpcfg` и `/f` работают наравне с `/DumpCfg` и `/F` | не проверяется |
| `/IBConnectionString` как способ задать базу | работает наравне с `/F` | пропускается |
| чужой инструмент (`ibcmd`, `rac`, `ras`) | на этой машине нет `ibcmd.exe`, проверить нечем | не судится вовсе |

Отдельно о двух строках, ставших предупреждениями. Оба ключа —
`/UsePrivilegedMode` в режиме DESIGNER и `-Format` при `/DumpCfg` — приложением 7
для этих мест не предусмотрены, то есть формально составу противоречат. Но
платформа 8.3.27.2325 обе команды приняла и выполнила верно, а правило 11 требует
не блокировать то, про что не показано, что оно не работает. Смысл в них
остаётся — потому предупреждение, а не молчание.

Направление разреза у режима именно такое, а не «любое несовпадение»: пакетную
операцию выполняет конфигуратор, и вне DESIGNER её выполнять некому — платформа
открывает сеанс и ждёт человека. Обратно это не работает: посторонний ключ
внутри пакетного DESIGNER мешает не больше, чем лишний аргумент.

## Чем доказывается «база обновлена»

Отдельная проверка того же дня, тем же способом. `/DumpDBCfg` выгружает
**конфигурацию базы данных**, `/DumpCfg` — основную. После успешного
`/UpdateDBCfg` они обязаны совпасть.

```
DESIGNER /F D:/1C/base/trade /DumpCfg main.cf   → код 0, 4973 байта
DESIGNER /F D:/1C/base/trade /DumpDBCfg db.cf   → код 0, 4973 байта
SHA256 обоих: 74BB37F6D110F3DEE0940DD7D9E4C9FA582949B9767B2B490A0A8A6B212213EE
```

База не изменялась между запусками, конфигурация базы данных совпадала с
основной — и выгрузки совпали побайтно. Это и есть проверка результата вместо
проверки отчёта: код возврата 0 был бы получен и при расхождении.

Перепрогон 23.08.2026 (задача 2), на выросшей с тех пор базе:

```
DESIGNER /F D:/1C/base/trade /DumpCfg main2.cf   → код 0, 75395 байт
DESIGNER /F D:/1C/base/trade /DumpDBCfg db2.cf   → код 0, 75395 байт
SHA256 обоих: 773C56E8E8C2609683B772FE8AF520296E3BBBDDFD7BA0F4D9E7B087C88D70F7
```

Совпадение снова побайтное — вывод не изменился, изменился только размер
базы между запусками.

## Третий раунд ревью задачи 3 (2026-08-23): блокировка распространена без прогона

Второй раунд (раздел выше, «Ревью задачи 3: формула «самое длинное среди
ВСЕХ» неверна») ввёл `absorbs_glued_tail` и заблокировал ВСЕ не-glued ключи,
которые в него попадают. Рецензент нашёл в этом Critical: `absorbs_glued_tail`
признаёт кандидатом на поглощение около пятидесяти не-glued ключей (`/S`,
`/WS`, `/C`, `/ConfigurationRepositoryF`, `/ConvertFiles`, `/DumpDBCfg` и
десятки других — каждый с «голым» `arg`), а живым прогоном из них проверены
были только три: `/LoadCfg`, `/DumpCfg`, `/Out`. Формула «не glued →
блокировать» — обобщение по признаку, а не по измерению, и первый же
прогон дал контрпример.

### Прогон

```
$exe = "C:\Program Files\1cv8\8.3.27.2325\bin\1cv8.exe"
$a = @('DESIGNER','/Snosuchhost9999:1541/nodb','/DisableStartupDialogs','/Out',"$w\l.log")
Start-Process -FilePath $exe -ArgumentList $a -Wait -PassThru -NoNewWindow -WorkingDirectory $w
```

```
код: 1
журнал: Ошибка при выполнении операции с информационной базой
        server_addr=nosuchhost9999 descr=11001(0x00002AF9): Этот хост неизвестен.
        line=585 file=src\core\src\Networking.cpp
```

`server_addr=nosuchhost9999` — платформа разобрала `/Snosuchhost9999:1541/nodb`
как `/S` со значением `nosuchhost9999:1541/nodb` ВЕРНО, ровно как документирует
раздел 7.3.1 (`/S<адрес сервера>[:<порт>][/<имя базы>]`). Отказ — из-за
несуществующего хоста (ошибка DNS), а не из-за разбора ключа. Найдено
рецензентом, воспроизведено координатором независимо тем же прогоном.

### Решение: блокировка только там, где есть свой прогон

`absorbs_glued_tail` остаётся моделью РАЗБОРА (какой ключ платформа
подставит) — она не изменилась и не опровергнута: `/S` действительно
резолвится через неё, и резолвится верно. Ошибка была в том, что из факта
«резолвится не в себя, не glued» код делал вывод «заведомо неверно» без
прогона. Теперь блокировка — по явному списку `PROVEN_TAIL_MISPARSE`,
и только эти три ключа в нём:

| Ключ | Чем доказано |
|---|---|
| `/LoadCfg` | запуском 2026-08-23: `/LoadCfgFromFile` → код 1, «Файл не обнаружен '…\FromFile'», файл-цель не создан |
| `/DumpCfg` | запуском 2026-08-22 (перепроверено 2026-08-23): `/DumpCfgToFile` → код 0, но выгрузка ушла в файл `ToFile`, не в указанный путь |
| `/Out` | запуском 2026-08-23: `/OutBase` → код 0, но лог ушёл в файл `Base`, не в указанный путь |

Остальные ~47 ключей семейства (`/S`, `/WS`, `/C`,
`/ConfigurationRepositoryF`, `/ConvertFiles`, `/DumpDBCfg` и другие) —
предупреждение с честным текстом «поведение платформы для этого
конкретного совпадения запуском не проверялось», без слов «проверено
запуском», которых не было.

### Шесть команд той же семьи — проверены на уровне check() (не все на живой платформе)

| Ключ | Резолвится в | Живым запуском | Результат после правки |
|---|---|---|---|
| `/S<адрес>` | `/S` | да (выше) | предупреждение, код 0 |
| `/WS<url>` | `/WS` | нет | предупреждение, код 0 |
| `/C<текст>` | `/C` | нет | предупреждение, код 0 |
| `/ConfigurationRepositoryF<каталог>` | `/ConfigurationRepositoryF` | нет | предупреждение, код 0 |
| `/ConvertFiles<файл>` | `/ConvertFiles` | нет | предупреждение, код 0 |
| `/DumpDBCfg<файл>` | `/DumpDBCfg` | нет | предупреждение, код 0 |

Только `/S` подтверждён отдельным прогоном (единственный, для которого он
был явно запрошен и сделан). Остальные пять — уже не блокируются (регресс
устранён), но текст предупреждения честно говорит «не проверялось» — они
не добавлены в `PROVEN_TAIL_MISPARSE` и не должны читаться как проверенные.
