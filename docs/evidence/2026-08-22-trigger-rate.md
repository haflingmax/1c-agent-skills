# Частота срабатывания навыка `developing-1c-configurations` (2026-08-22)

Замер: `tools/measure-trigger.ps1`. Шесть формулировок задачи, в двух средах,
до и после правки поля `description` ядра. Между замерами:
`powershell -NoProfile -File tools/install-skills.ps1`.

Мера — **только поле `Навык`**: у Kilo это баннер вызова в журнале
(`→ Skill "developing-1c-configurations"`), у Claude Code — структурный
элемент `tool_use` с именем `Skill` в потоке `stream-json`. Поле `Вопросов`,
которое тоже возвращает `tools/run-prompt.ps1`, в этот замер не включено:
оно дважды дало ложные срабатывания — считало вопросом тернарный оператор
1С `?(Условие, Если, Иначе)` внутри сгенерированного кода и объявление
`<?xml version...?>`. Чем больше кода писал агент, тем «назойливее» он
выглядел бы по этому полю — оно не о том, поднялся ли навык.

## Правка

Старая формулировка (перечень тем):

```
Разработка конфигураций 1С:Предприятие 8.3 по исходникам — от планирования доработки до кода. Применяется, когда в задаче справочник, документ, регистр, форма, запрос, отчёт, обработка, роль, расширение, БСП, СКД или файлы .bsl, .epf, .cf.
```

Новая формулировка (последствие для ответа, а не тема), 332 знака — под
потолком 340:

```
Разработка конфигураций 1С:Предприятие 8.3 по исходникам — от планирования доработки до кода. Применяется, когда ответ должен соответствовать стандартам 1С и соглашениям типовых конфигураций, а не общему знанию языка: справочник, документ, регистр, форма, запрос, отчёт, обработка, роль, расширение, БСП, СКД, файлы .bsl, .epf, .cf.
```

## Вывод по каждой среде

- **Kilo (minimax-m3): было 5 из 6, стало 5 из 6 — без изменений.** Ряд
  совпадает построчно: те же пять формулировок подняли навык и до, и после
  правки, та же одна («Поправь проведение документа Реализация.») — нет,
  в обоих срезах. Для этой среды и этого набора формулировок правка
  description рычагом не стала: Kilo решает вызывать навык по тем же
  сигналам, что и раньше, независимо от того, названа ли причина темой или
  последствием.

- **Claude Code: было 5 из 6, стало 6 из 6 — выросло на одну формулировку.**
  Единственная разница — «Сделай отчёт по продажам за месяц.»: до правки
  навык не поднимался (`False`), после — поднимается (`True`). Остальные пять
  формулировок не изменились (все уже были `True` до правки, кроме одной
  разошедшейся). Для Claude Code правка сработала — но не как «включила
  навык там, где его не было вовсе», а как закрыла один пограничный случай:
  простую задачу, где модель раньше решила, что справится общим знанием
  языка, и её решение изменилось именно после того, как description стал
  говорить о соответствии стандартам, а не о списке тем.

**Расхождение между средами — не сбой замера, а факт: выросло в одной среде
(Claude Code) и не выросло в другой (Kilo).** Это соответствует ожиданию
раздела 4 брифа: цель — «сработал там, где стандарты решают исход», а не
«сработал везде одинаково». В Kilo на этих шести формулировках такого случая
не нашлось; в Claude Code нашёлся один.

## Сырые данные

Полный, построчный журнал прогона (включая служебные события `stage-done`,
`desc-changed`, `install`) сохранён в JSON Lines по ходу замера. Он не входит
в состав репозитория (временный файл прогона), но воспроизводим повторным
запуском `tools/measure-trigger.ps1`.

Один прогон стадии «после» пришлось переснять: при доснятии части замера
(после того как первый сквозной прогон уже собрал стадию «до», применил
правку и переустановил навыки, но был прерван платформой на стадии «после»)
передача двух формулировок одним вызовом PowerShell из-под POSIX-оболочки
слиплась в одну строку по запятой («Напиши запрос 1С по остаткам
номенклатуры.,Сделай отчёт по продажам за месяц.») — эта строка отброшена
как артефакт вызова, не как измерение, и обе формулировки переснова́ны по
отдельности (видно в таблицах выше как обычные строки).
