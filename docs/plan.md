# План работ над набором навыков 1С

Рабочий документ. Ведётся, чтобы решения не пересматривались по кругу, а найденные
дефекты не терялись. Обновлять при каждом принятом решении.

Состояние на 22.08.2026.

## Замысел

Набор навыков для разработки конфигураций 1С:Предприятие 8.3 по исходникам. Публикуется
как маркет-плагин (Claude Code, Codex) и как отдельные навыки для копирования. Работает
в трёх средах: Claude Code, Kilo Code, Codex.

Строится в два приёма: сначала ядро с раскладкой разделов, потом остальные разделы —
своими силами, по ИТС.

Два сторонних набора по 1С прочитаны как **референс**: они показывают, что вообще стоит
покрыть, и подсказывают удачные ходы. Материал из них не переносится (решение 16).

### На чём стоят референсы

Главная находка обоих проходов. Из 78 единиц описи данных на официальную
документацию 1С опирается **одна** — `query-optimization-tips.md`.

| На чём основано | Единиц |
|---|---|
| опыт автора | 34 |
| не сказано | 23 |
| разбор конфигураций | 18 |
| смешанно | 3 |
| **ИТС** | **1** |

«Разбор конфигураций» — обратная разработка выгрузок, и авторы это пишут прямо:
«на основе анализа 7723 форм», «930 схем СКД», «10 924 макета ERP», «корпус
760 пакетов». Работа добросовестная, но первоисточником не является.

Отсюда практическое следствие для РАЗБОР-2: **сверять придётся всё.** Решение 16
требует опоры на ИТС не из принципа — у референсов её попросту нет, и совпадение
нашего текста с их текстом ничего не доказывает.

Читатели нашли пять прямых противоречий между двумя версиями одного документа,
каждое зафиксировано без попытки рассудить:

- права `ExternalDataSource` в ролях — одна версия помечает утверждение другой
  как ошибку прежних редакций;
- версия платформы, где появилось свойство `TypeReductionMode`: 8.3.25 против 8.3.27;
- порядок дочерних свойств формы: строгий (доказано на 30 223 формах) против произвольного;
- атрибут `enableStandardOdata`: устаревший и нерабочий против рабочего;
- поведение `DataPath` при заимствовании формы в расширение.

Производный набор развивался не только вычитанием: у `db-guide.md` версии
разошлись в обе стороны — у исходного уникальный эмпирический блок со сравнением
движков, у производного свои навыки, которых в исходном нет.

## Принятые решения

Не пересматривать без нового основания.

1. **15 разделов.** Сначала было 13; сверка с полным деревом v8std (318 стандартов, из них
   212 действующих для 8.3) добавила три — `1c-security`, `1c-libraries-bsp`,
   `1c-localization`. **23.08.2026 решением 17 `1c-libraries-bsp` убран**: специфика БСП —
   предмет отдельного набора. Область v8std «Разработка и использование библиотек»
   (9 стандартов) остаётся вне охвата сознательно; набор закрывает 203 стандарта из 212.
2. **Безопасность отделена от прав.** «Настройка прав доступа» (роли, RLS, профили) и
   «Общие вопросы безопасности» (`Выполнить` на сервере, внешний код, пароли, внешние
   ресурсы) — разные задачи разработчика.
3. **Регламентные задания остаются в `1c-client-server`**, хотя ИТС относит их к метаданным:
   стандарты описывают расписание, запуск и ограничения в режиме сервиса, то есть исполнение.
4. **Бухгалтерия, периодические расчёты, бизнес-процессы — в `1c-metadata-objects`**
   (главы 11–13 руководства разработчика). Вопрос об отдельном разделе открывается заново,
   только если написанный материал туда не влезет.
5. **Раздела «прочие механизмы платформы» не будет.** Главы 20, 22–25, 29, 32 разложены по
   существующим разделам. Общего у них только то, что они не попали в систему стандартов, —
   раздел по такому признаку агент по описанию не выберет.
6. **Три режима работы** набора: А — внутри конвеера superpowers; Б — голый навык на разовой
   задаче; В — операция с платформой без планирования.
7. **superpowers — рекомендация, не зависимость.** Базовый режим — навык сам по себе.
   Никаких жёстких требований в `plugin.json`; ядро не должно предполагать его наличие.
8. **Правила делятся на правила плана и правила реализации.** Основание: решение уровня плана,
   принятое на реализации, даёт заведомо неверный код.
9. **Документация ИТС в набор не попадает.** Корпус (7,5 млн знаков) остаётся локально как
   сырьё. Публикуется только наше изложение, организованное по задачам. Это ответ и по
   соглашению с 1С, и по объёму: корпус в девять раз больше окна контекста.
10. **Четыре слоя подачи справочного материала:** незыблемые правила в ядре (всегда) →
    рецепт задачи (по совпадению) → справочник ключей (по требованию) → проверяльщик-скрипт
    (детерминированно). Предложено и сверено с архитектурой; правки см. в открытых вопросах.

11. **Новых навыков не заводим.** Раскладка остаётся 15 разделов плюс ядро (было 16 — см. решение 17). Основание —
    потолок каталога Codex (8000 знаков): каждый лишний навык оплачивается чужими
    описаниями. Проекты с отдельным навыком-планировщиком и с тремя навыками-входами
    отвергнуты по этой причине. **Уточнено 22.08.2026:** «73% бюджета» здесь считались от
    описания ядра в 344 знака, которого больше нет. Считать надо произведение, а не число
    навыков: 16 × 240 = 3840 знаков (без малого половина бюджета), 16 × 332 = 5312 (две трети).
    Числа пересчитаны 23.08.2026 после исключения `1c-libraries-bsp`: было 17 навыков, стало 16.
    Единственное место, где это правило живёт, — правило 9 архитектуры; здесь только вывод.
12. **Правила плана живут в теле ядра, а не в `references/`.** Основание — Д-9: в Kilo файлы
    навыка недостижимы, а тело доставляется инструментом `skill` и чтения не требует.
    Место есть: ядро ~2,5 тыс. токенов при пределе 5 тыс.
13. **Восьмое правило архитектуры — признак необратимости.** Правило относится к плану, если
    его нарушение нельзя исправить правкой кода: требуется менять структуру данных,
    перезаписывать данные, менять режим совместимости или получать согласие владельца.
    Всё остальное — правила реализации. К этой формулировке независимо сошлись все три проекта.
14. **Разделы не укрупняются; длина описания назначается замером, а не потолком.**
    Слияние разделов уничтожило бы раскладку по областям знания, сверенную с ИТС по
    318 стандартам. **Пересмотрено 22.08.2026 по новому основанию** — замеру частоты
    срабатывания (`docs/evidence/2026-08-22-trigger-rate.md`): прежняя формулировка
    «описания ужимаются до 180–200 знаков» противоречила собственной правке ветки, поднявшей
    описание ядра до 332 знаков ради одной задачи из шести в Claude Code. Бюджет держится
    числом навыков и краткостью тех описаний, которым длина ничего не даёт
    (`1c-build-and-db` — 228 знаков), а не единым потолком на каждое.
15. **Деградация по наблюдаемому признаку, не по среде.** Ветвление на «готовится ли документ
    плана», а не на «установлен ли superpowers». `dependencies` в `plugin.json` не ставим:
    мягкой зависимости в формате нет, а `{"name": "superpowers", "optional": true}` — ловушка,
    проходит проверку молча и оставляет зависимость жёсткой, убивая весь набор при отсутствии
    плагина.
16. **Мы не делаем форк и ничего не переносим.** Решение владельца 23.08.2026,
    связывает весь этап РАЗБОР. Набор создаётся свой, без зависимостей от двух
    референсных и без ссылок на них из тела навыков. Референсы отвечают ровно
    на один вопрос — **что вообще стоит покрыть** — и подсказывают удачные ходы;
    ответом на вопрос «как именно» они не являются.

    **Три столпа.** Каждое утверждение в навыках опирается на один из трёх
    источников и ни на что другое:
    - официальная документация Anthropic — контракты навыков и плагинов;
    - **наше утверждённое ядро** — архитектура, раскладка 16 разделов, правила плана
      и реализации, деление на необратимое и поправимое;
    - **ИТС** — истина по 1С: стандарты, руководства разработчика и администратора.

    Следствия, обязательные к соблюдению на РАЗБОР-2:
    - совпадение нашего текста с референсным не является доказательством; доказательством
      является ссылка на ИТС. Референс может ошибаться, и уже ошибается: опись нашла
      навыки, ссылающиеся на несуществующие навыки, и параметр, описанный в справочнике
      и отсутствующий в таблице;
    - ни текст, ни код референсов не переносятся. Пишем своё по ИТС; референс мог лишь
      подсказать, что тема существует и что о ней стоит подумать;
    - расхождение двух версий референса — не спор, который нам разрешать. Обе версии
      это лишь два мнения; выбор делается сверкой с ИТС, а не подсчётом, кто полнее.

    **`ATTRIBUTION.md` удалён 23.08.2026** этим же решением. Файл описывал порядок
    заимствования и обязывал помечать заимствованные файлы ссылкой на источник —
    помечать больше нечего. Юридически он тоже не нужен: MIT требует сохранять
    уведомление при использовании кода или текста, а мы не берём ни того, ни другого.
17. **Охват набора: платформа 8.3 и общие вопросы разработки.** Решение владельца
    23.08.2026. Одним набором всё не покрыть, и попытка покрыть даёт набор, который
    не годен ни для чего конкретного.

    **Только платформа 8.3, любая подверсия.** 7.7 — иная платформа с иными форматами.
    Интерфейсы 8.2 и обычное приложение уже были сознательно вне охвата (правило 12
    архитектуры, 106 стандартов); теперь это сказано и в теле ядра, а не только
    в справочнике.

    **Только общие вопросы разработки.** Правил под конкретную типовую конфигурацию
    в этом наборе нет и не будет: соглашения ЕРП, БП и ЗУП различаются между собой
    и меняются от релиза к релизу. Такие правила пойдут отдельными наборами в этом же
    маркете — по набору на конфигурацию, каждый со своим сроком жизни и своим владельцем
    предметной области.

    **БСП вне охвата.** Решение владельца 23.08.2026, принятое в два хода: сначала БСП
    оставили с требованием называть версию, затем исключили целиком. Основание для
    исключения — то же, что делало требование версии необходимым: библиотека живёт своим
    циклом версий, её API между ними расходится, и общий совет, выданный за правило БСП,
    верен не для всякой версии. Специфика БСП пойдёт отдельным набором, где не будет
    общих вопросов платформы — только библиотека.

    Раздел `1c-libraries-bsp` убран из раскладки; разделов стало 15. Область v8std
    «Разработка и использование библиотек» (9 стандартов) вне охвата сознательно.

    **Ссылки на будущий набор в тексте нет — и не будет, пока набор не выпущен.**
    Ссылка на несуществующее — обещание, которое агент передаст пользователю как
    выполнимое: «поставьте набор по БСП», которого нет. Вместо ссылки в ядре стоит
    поведение: узнал БСП по коду — скажи вслух, что это БСП и что её специфика вне
    охвата, и не выдумывай её API по памяти. Платформенная часть той же задачи
    остаётся за набором. Когда набор по БСП появится, ссылку можно будет добавить
    одной строкой — правило выпуска для этого уже есть.

    Следствие для описи референсов: единицы вроде `zup-hr-api-reference` (справочник
    прикладного API ЗУП) отсекаются этим правилом, а не разбираются поштучно. Читатели
    отнесли их «вне раскладки» независимо, до появления правила.

## Приёмка ядра

Владелец утвердил ядро 22.08.2026 с условием: приёмке предшествует полное ревью
по четырём осям.

1. Соответствие документации и требованиям к навыкам и плагинам Claude и Codex.
2. Логические и технические ошибки.
3. Сравнение с лучшими наборами навыков **не про 1С**.
4. Лучшее из других экосистем и языков.
