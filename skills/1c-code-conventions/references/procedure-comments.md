# Документирующий комментарий процедуры и функции

Стандарт 453 «Описание процедур и функций», область применения — «управляемое
приложение, мобильное приложение, обычное приложение». В заголовке раздела
на ИТС стоит пометка «(Раздел обновлен!)».

Формат здесь не косметический: «текст комментария также выводится в контекстной
подсказке процедур, функций и их параметров», а в 1C:Enterprise Development
Tools «используется для уточнения типизации параметров и возвращаемого
значения… и тем самым помогает выявлять ошибки кодирования на этапе
разработки». Комментарий не по формату — это потерянная типизация, а не только
неопрятность.

## Кого комментировать обязательно

**Обязательно** (пункт 2): «процедуры и функции входящие в программный
интерфейс модулей — такие процедуры и функции предназначены для использования
в других функциональных подсистемах (или в других приложениях), за которые
могут отвечать другие разработчики, поэтому они должны быть хорошо
документированы. **В остальных случаях комментарий может, как отсутствовать,
так и быть произвольным текстом.**»

**Прочие — по необходимости** (пункт 3): «рекомендуется комментировать, если
требуется пояснить назначение процедуры (функции) или особенности её работы.
Также рекомендуется описывать **причины невыполнения** некоторых действий,
если они кажутся неочевидными». И прямо: «если процедура (функция) не сложна
для понимания и ее назначение и порядок работы следуют из ее названия и имен
формальных параметров, комментарий **допускается не писать**».

**Пустой комментарий хуже отсутствующего** (пункт 4): «Следует избегать
комментариев, не дающих дополнительных пояснений о работе не-экспортной
процедуры (функции)». Примеры «неправильно» из источника — ровно те
комментарии, которые пишутся машинально:

```bsl
// Процедура - обработчик события "ПриОткрытии" формы
//
&НаКлиенте
Процедура ПриОткрытии()

// Функция возвращает статью движения денежных средств по данным документа
Функция СтатьяДвиженияДенежныхСредств(ДанныеДокумента)
```

## Секции комментария

Комментарий «размещается **перед** объявлением процедуры (функции)».
Секций пять: «Описание», «Параметры», «Возвращаемое значение», «Пример»,
«Варианты вызова». Английские имена: `Description`, `Parameters`, `Returns`,
`Example`, `Call options`.

### Описание (5.1)

«Содержит описание назначения процедуры (функции), достаточное для понимания
сценариев ее использования **без просмотра ее исходного кода**».

- «Может быть единственной секцией для процедур без параметров»;
- «Описание **не должно совпадать с именем** процедуры (функции)»;
- «секция **должна начинаться с глагола**. Для функций это, как правило:
  "Возвращает…". В тех случаях, когда возвращаемый результат является
  не основным в работе функции, — то с основного действия, например:
  "Проверяет…", "Сравнивает…", "Вычисляет…"»;
- «**Не рекомендуется** начинать описание с избыточных слов "Процедура...",
  "Функция...", а также с имени самой процедуры (функции), от удаления которых
  смысл не меняется».

### Параметры (5.2)

«Если их нет, секция пропускается. Предваряется строкой "Параметры:", затем
с новой строки размещаются описания всех параметров».

**Форма строки** (5.2.1): «имя параметра, затем дефис и список типов, далее
дефис и текстовое описание параметра».

**Тип обязателен**: «Описание типа является **обязательным**». «Под "списком
типов" подразумеваются имена типов, разделенные запятыми. Имя типа может быть
простым (в одно слово) или составным — в два слова, разделенных точкой.
Например: `Строка`, `Структура`, `Произвольный`,
`СправочникСсылка.Сотрудники`».

«В качестве типов значений следует использовать **только существующие
в платформе типы**, а также специальные типы, предусмотренные в EDT:
`ОпределяемыйТип.<Имя>`, `СправочникСсылка`, `ОбъектМетаданныхОтчет`,
`РасширениеДекорацииФормыДляНадписи` и т.п.»

```
// Неправильно:
// КоллекцияСтрок - КоллекцияЗначений – коллекция для сравнения;
// ФормируемыйОтчет - ОбъектМетаданных: Отчет
// ПрисоединенныйФайлОбъект - элемент справочника файлов.

// Правильно:
// КоллекцияСтрок – ТаблицаЗначений, Массив, СписокЗначений – коллекция для сравнения.
// ФормируемыйОтчет – ОбъектМетаданныхОтчет
// ПрисоединенныйФайлОбъект - ОпределяемыйТип.ПрисоединенныйФайлОбъект - элемент справочника файлов.
```

**Текстовое описание — не всегда**: «рекомендуется заполнять в том случае,
когда только имени параметра в контексте функции не достаточно для понимания
его назначения, либо требуется дать дополнительную информацию о типе… а также
может приводиться наглядный пример с ожидаемым значением параметра».

**Структура и таблица значений** (5.2.2): «в описании типа **необходимо**
указывать ссылку на функцию, выходным значением которой является эта структура
или таблица значений. Например, ссылку на функцию-конструктор»:

```bsl
// ПараметрыЗаполненияЦен – см. ЦенообразованиеСервер.ПараметрыЗаполненияЦен
```

Исключение оттуда же: «В редких случаях, когда метод обрабатывает коллекции
универсальным образом, не нужно описывать свойства и колонки параметра».

**Массив** (5.2.3): «следует указывать тип элементов с помощью ключевого слова
"из" (англ. "of")»:

```bsl
// СведенияОбОбновлении - Массив из см. ОбновлениеИнформационнойБазы.ПараметрыОбновления
```

«Допускается не указывать тип элементов массивов **только** в методах, которые
работают с массивами универсальным образом».

**Строка таблицы значений** (5.2.4):

```bsl
// СведенияОРегионе – СтрокаТаблицыЗначений: см. РегистрыСведений.АдресныеОбъекты.КлассификаторСубъектовРФ
```

**Дополнительные типы одного параметра** (5.2.5): «Каждое дополнительное
описание начинается с новой строки, затем **обязательный дефис**, далее список
типов параметра далее дефис и текстовое описание»:

```bsl
// Параметры:
//  Реквизиты - Строка - имена реквизитов, перечисленные через запятую.
//             Например, "Код, Наименование, Родитель".
//           - Структура, ФиксированнаяСтруктура - в качестве ключа передается
//             псевдоним поля для возвращаемой структуры с результатом.
//           - Массив Из Строка, ФиксированныйМассив Из Строка - имена реквизитов.
```

**Ссылка вместо описания** (5.2.6) — формат «см. ПутьКФункции» (англ.
«see MethodPath»).

### Возвращаемое значение (5.3)

«Для процедур эта секция отсутствует. Предваряется строкой "Возвращаемое
значение:". Затем с новой строки тип возвращаемого значения, дефис и текст
описания. При использовании возвращаемого значения **составного типа следует
каждый тип писать с новой строки и с дефиса**»:

```bsl
// Возвращаемое значение:
//  - ЛюбаяСсылка - ссылка на предопределенный элемент.
//  - Неопределено - если предопределенный элемент есть в метаданных, но не создан в ИБ.
```

### Пример (5.4)

«Имя процедуры (функции) следует писать **вместе с именем общего модуля**,
в котором она расположена. Из примера должно быть понятно, что передается
на входе и что возвращается на выходе».

```bsl
// Неправильно:
// Пример:
//  ПодставитьПараметрыВСтроку(ШаблонСтроки, СтрокаЗамены);

// Правильно:
// Пример:
//  СтроковыеФункцииКлиентСервер.ПодставитьПараметрыВСтроку(НСтр("ru='%1 пошел в %2'"), "Вася", "Зоопарк") = "Вася пошел в Зоопарк".
```

**В переопределяемых модулях — наоборот** (5.4.1): «в секции "Пример" следует
размещать **пример реализации** переопределяемой процедуры, а не пример
ее вызова».

### Варианты вызова (5.5)

«В редких случаях, когда сразу несколько параметров имеют дополнительные типы».
«Каждый вариант вызова представляется в виде имени функции со списком типов,
перечисленных через запятую в круглых скобках, затем следует дефис и текстовое
описание варианта».

## Отступы (5.6)

«Текст комментария во всех **объявляемых** секциях должен иметь отступ
относительно заголовка секции, начиная с первой строки. В многострочном
описании, относящемся к одному контексту, дополнительный отступ требуется
**только для второй строки**. Для следующих строк отступ не требуется — строки
выравниваются по одной вертикали со второй».

Зачем — сказано прямо: «для корректного отнесения текста к той или иной секции
**автоматизированными средствами** в случаях, когда имеются ошибки оформления».

Секция «Описание» — **не** объявляемая, поэтому её вторая и последующие строки
пишутся без отступа.

## Ссылки и пометка «Устарела»

**Переход** (5.7): «В любом месте документирующего комментария можно добавить
переход к другим объектам конфигурации, процедурам и функциям… При
использовании 1C:Enterprise Development Tools среда оформит такие переходы
в виде гиперссылки»: `// См. УправлениеДоступом.ЗаполнитьНаборыЗначенийДоступа`.

**Устаревшее** (5.8): «в **первой строке** ее описания размещается слово
"Устарела" (англ. "Deprecated")»:

```bsl
// Устарела. Следует использовать см. ОбщегоНазначения.РазделениеВключено и
// см. ОбщегоНазначения.ДоступноИспользованиеРазделенныхДанных
```

## Комментарий и директива компиляции (пункт 6)

«вначале следует размещать комментарий, а затем — директиву компиляции»:

```bsl
// Обрабатывает параметры формы и заполняет реквизиты формы значениями.
//
&НаСервере
Процедура ПриСозданииНаСервере(Отказ, СтандартнаяОбработка)
```

Причина названа: «позволяет в первую очередь обращать внимание на определение
функции и директиву компиляции, а потом — на комментарий, который может
занимать достаточно большое количество строк».

## Пустые строки (пункт 7)

«Код процедур и функций **должен** отделяться друг от друга в тексте модуля
пустыми строками».

## Сквозной образец из стандарта

```bsl
// Определяет доступность ролей ИменаРолей текущему пользователю,
// а также доступность административных прав.
//
// Параметры:
//  ИменаРолей - Строка - имена ролей, доступность которых проверяется, разделенные запятыми.
//
// Возвращаемое значение:
//  Булево - Истина, если хотя бы одна из переданных ролей доступна текущему пользователю,
//           либо у него есть административные права.
//
// Пример:
//  Если РолиДоступны("ИспользованиеРассылокОтчетов,ОтправкаПоПочте") Тогда ...
//
Функция РолиДоступны(ИменаРолей) Экспорт
```
