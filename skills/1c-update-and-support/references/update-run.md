# Как идёт обновление: от файла до конфигурации базы данных

**Ищут по словам:** обновить конфигурацию, помощник обновления, обновление
конфигурации базы данных, реструктуризация, монопольный доступ, завершить
сеансы, динамическое обновление, версия изменений конфигурации, фоновое
обновление, `КонфигурацияИзмененаДинамически`, вернуться к конфигурации базы
данных.

Источники: руководство разработчика, §38.3.4 «Обновление конфигурации», §2.14
«Обновление конфигурации базы данных» со всеми подпараграфами, §2.14.3
«Фоновое обновление», приложение 8 (СУБД).

Правила про динамическое обновление и его умолчание стоят **в теле навыка**;
здесь ход операции целиком.

## Обновление — это две разные операции подряд

Первая: **обновить конфигурацию** из файла поставщика (§38.3.4) — сравнение
и объединение, результат ложится в основную конфигурацию. Вторая: **обновить
конфигурацию базы данных** (§2.14) — только после неё изменения начинают
исполняться.

Между ними база работает по-старому, и это состояние — норма, а не поломка.
Путать их дорого: «обновление прошло» после первой операции не означает
ничего для пользователей.

## Первая операция: помощник обновления (§38.3.4)

Помощник ищет файл обновления в трёх местах: «текущий каталог шаблонов»,
съёмные диски и «адрес, указанный в конфигурации как адрес каталога
обновления».

**Подсказка помощника — не гарантия:** в списке найденных обновлений «жирным
шрифтом выделяется обновление, которое наиболее вероятно подходит для
обновления конфигурации».

**И предупреждение, которое источник ставит отдельно:** «необходимо отчетливо
понимать, что источник, из которого получен файл обновления конфигурации,
является надежным и действительно содержит обновление используемой
конфигурации, без нежелательных модификаций».

Дальше открывается обычное окно сравнения и объединения — разбор
в `merge-modes.md`.

**Одна ловушка именно этого окна:** «Если разработчик не сохранил результат
объединения, то текст модуля не меняется, и объединение конфигураций
продолжается». Обновление считается выполненным со старым модулем.

## Вторая операция: обновление конфигурации базы данных (§2.14.2)

**Оно молча сохраняет основную конфигурацию:** «Если основная конфигурация еще
не была сохранена, то сначала конфигуратор выполнит ее сохранение, а потом
произведет обновление конфигурации…». Незаписанные эксперименты после этого
отменяются только возвратом к конфигурации базы данных — то есть потерей всего.

**Оно требует монополии:** «Обновление конфигурации базы данных требует
монопольного доступа конфигуратора к информационной базе», и «может
потребовать прекращения работы всех пользователей».

**Оно гасит отладку:** «Для обновления конфигурации базы данных необходимо
прекратить отладку. Продолжить?»

**И очищает окно сообщений:** «Если при обновлении конфигурации базы данных
было открыто окно сообщений, то оно очищается» — диагностика предыдущего шага
пропадает.

## Три исхода при занятой базе (§2.14.2.1–2.14.2.2)

**Ошибка блокировки** — когда обойти нельзя: конфигуратор «выдает сообщение
об ошибке исключительной блокировки в том случае, если: используется файловый
вариант базы данных; есть сеансы…» и далее по перечню четырёх условий.
Обхода из конфигуратора нет: «имеется возможность только дождаться, пока
пользователи будут отключены от информацион…».

**Предложение завершить сеансы** — в другом наборе условий: «конфигуратор
предлагает завершить все сеансы и повторить обновление, если: обновление
конфигурации требует реструктуризации базы данных; с ф…». И оно означает ровно
то, что написано: «Завершение сеансов приведет к **аварийному завершению
работы пользователей**! Выполнить завершение сеансов?»

**Динамическое обновление — во всех остальных случаях:** «в остальных случаях
конфигуратор предлагает выполнить динамическое обновление». Это и есть путь
по умолчанию, и он не меняет конфигурацию базы данных (правило в теле).

**Подробность диагностики зависит от числа сеансов:** «Если количество сеансов
меньше или равно 5, то выводится подробный список сеансов (с указанием имени
компьютера, типа приложения и т. д.), в…» — иначе только количество.

## Что ещё надо знать о динамическом обновлении (§2.14.2.2.3)

**Оно накапливается:** «Допускается выполнение повторных изменений основной
конфигурации. Если при очередной попытке обновления конфигурации базы данных
может быть…» выполнено динамическое — версии накапливаются.

**И стирается полноценным обновлением:** «После выполнения обновления
конфигурации базы данных все версии, созданные динамическим обновлением, будут
удалены».

**Узнать о нём из кода можно:** «Для контроля и оповещения пользователей
о произведенных динамических изменениях следует использовать метод глобального
контекста КонфигурацияБазыДанныхИзмененаДинамически()».

**Имя читать целиком.** В нём есть «БазыДанных», и без этой части получается
`КонфигурацияИзмененаДинамически` — а это не метод платформы, а строковый код
ошибки из пространства имён БСП («СтандартныеПодсистемы.БазоваяФункциональность.
КонфигурацияИзмененаДинамически», `std` про вызов исключений). Два похожих
имени из разных миров: одно вызывается, второе сравнивается со строкой.

Метод — штатный способ для прикладного кода понять, что база исполняет не то,
что лежит в конфигурации.

## Фоновое обновление: сильные ограничения (§2.14.3)

**Лицензия и вариант работы:** «Доступно только для лицензии КОРП» и только
в клиент-серверном варианте. Вид лицензии при этом прикладному коду
не виден — это вывод набора: прямого утверждения источники не дают,
а `std791` косвенно подтверждает, требуя решать вопрос лицензии
проектно и держать «только одну ветку кода».

**Не работает** при режиме совместимости 8.1, при подключённых расширениях,
расширяющих данные, и на IBM Db2 9.1.

**Фаза принятия изменений всё равно монопольная**, и «Фаза актуализации всегда
выполняется на сервере» — выигрыш фонового обновления в том, что монопольной
становится только она.

**Пауза не вечна:** «Фоновое обновление конфигурации можно поставить „на паузу"
длительностью не более 48 часов. Если „пауза" продлится более 48 часов ‑
фоновое обновление будет отменено».

**И пока оно идёт, заперто больше, чем кажется.** «Во время фонового обновления
недоступны следующие операции», и в перечне три ожидаемых — «Редактирование
конфигурации», «Отладка прикладного решения», «Выполнение операции обновления
конфигурации базы данных» — и два неожиданных:

- «Не допускается использование методов УстановитьРежимАгрегатов(),
  УстановитьИспользованиеАгрегатов(), ПерестроитьИспользованиеАгрегатов()»;
- «Изменение содержимого плана счетов или плана видов расчета, если связанный
  с ним регистр бухгалтерии или регистр расчета участвует в операции фонового
  обновления. Попытка изменить содержимое таких планов счетов или планов вида
  расчета вызывает ошибку».

Последнее бьёт по прикладной работе, а не по разработке: план счетов правят
бухгалтеры, и ошибку увидят они. Выигрыш фонового обновления в том, что
пользователи работают, — но не все и не со всем.

**И одна подмена в диалоге:** флажок «Разрешить динамическое обновление»
превращает нажатие «Запустить» в динамическое обновление «вместо запуска
процесса фонового обновления конфигурации базы данных». Две разные операции
за одной кнопкой, обе отчитываются об успехе.

## Реструктуризация: от чего зависит длительность

**Механизм с 8.3.10 оптимизированный**, но выбирается настройкой, и «механизм
фонового обновления не связан с выбором механизма реструктуризации».

**Режим восстановления СУБД влияет:** «Для ускорения процесса реструктуризации
информационной базы, при использовании СУБД Microsoft SQL Server, рекомендуется
режим восстановления…».

**И одна оговорка, снимающая ложное успокоение:** «Работа информационной базы
в монопольном режиме **не переводит** базу данных Microsoft SQL Server
в однопользовательский (single user) режим».

## Ошибка, которая не выстрелит на обновлении

Приложение 8 (MS SQL Server): «Если запись индекса занимает более 900 байт,
то ошибка будет происходить **не в момент обновления конфигурации базы
данных**, а во время попытки вставки значения…».

То есть успешно прошедшее обновление не доказывает, что структура пригодна:
отказ придёт позже, на записи данных пользователем.

## Чего в §38.3.4 и §2.14 нет

- **отката обновления как темы:** в главе 38 нет ни одного вхождения корня
  «отмен»; единственный ход назад — «Вернуться к конфигурации базы данных»,
  то есть потеря всей несохранённой работы, и при подключённом хранилище эта
  команда недоступна;
- **проверки файла обновления** до его применения: источник ограничивается
  требованием доверять источнику файла;
- **что делать с расширениями** при обновлении поставщика: корень «расширен»
  в главе 38 не встречается ни разу.
