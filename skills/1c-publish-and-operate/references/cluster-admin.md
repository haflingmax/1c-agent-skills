# Кластер: что делают команды консоли и чего они не делают

**Ищут по словам:** консоль кластера, завершение сеанса, прерывание
серверного вызова, удаление соединения, PostgreSQL и разрыв соединения,
удаление кластера, удаление рабочего сервера, требования назначения
функциональности, применить требования, администраторы кластера,
аутентификация администраторов.

Источник: «Клиент-серверный вариант. Руководство администратора», раздел
«Администрирование» (§5.2). Ограничение потребления ресурсов и система
мониторинга — у соседа `1c-quality-gates`.

Правило про то, что здесь решает владелец системы, стоит **в теле навыка**.

## Консоль показывает снимок, а не состояние

«При работе с консолью администратора следует помнить, что информация,
отображаемая консолью, не обновляется автоматически. Для получения актуальной
информации, необходимо использовать команду консоли Действия ‑ Обновить»
(§5.2.1).

Отсюда первое правило работы: решение «сеансов нет, можно гасить»
принимается **после нажатия «Обновить»**, а не по тому, что на экране.
При разборе происшествия это первый источник ошибки.

## Свежий кластер пускает кого угодно

«По умолчанию список администраторов центрального сервера пуст. Это
означает, что…» административные функции доступны любому подключившемуся.
То же сказано про кластер: «По умолчанию список администраторов кластера
пуст».

**И администратор без вида аутентификации не защищает ничего:** «Если для
администратора не указан ни один из видов аутентификации, то такой»
администратор не ограничивает доступ.

Первый вопрос при разборе чужого кластера — **не «кто администратор»,
а «есть ли вообще список»**.

## Удаление сеанса: тихо для одного, дорого для данных

«Если в удаляемом сеансе нет серверного вызова, то сеанс будет удален без
вывода каких-либо сообщений пользователю. При попытке выполнить какое-то
действие в клиентском приложении, которое использовало удаленный сеанс,
пользователь получит стандартную ошибку Сеанс отсутствует или удален»
(§5.2.11.3).

Сообщение, набранное администратором, до такого пользователя **не дойдёт**:
он узнает о случившемся при следующем действии и в чужой формулировке.

**И цена названа врезкой:** «ВНИМАНИЕ! К использованию инструмента прерывания
серверного вызова или удаления сеанса следует подходить с осторожностью,
так эти действия могут привести к потере данных, которые обрабатываются
пользователем» (орфография источника).

**Порядок при удалении:** «При удалении сеанса вначале выполняется прерывание
текущего серверного вызова, а затем происходит удаление сеанса. Если в момент
завершения сеанса этот сеанс назначен соединению, то выполняется попытка
разрыва соединения». То есть удаление сеанса наследует все ограничения
разрыва соединения — включая следующее.

## На PostgreSQL разрыв соединения не делает ничего

«Удаление соединения для базы данных PostgreSQL невозможно. При попытке
выполнения команды удаления никаких действий выполнено не будет»
(§5.2.12.3).

**Ни ошибки, ни отказа.** Администратор считает, что выгнал пользователя,
а тот продолжает работать. Для MS SQL, Db2 и Oracle попытка делается
и удаётся при наличии прав у пользователя базы данных.

Это главное «молчание» раздела: команда, которая на одной СУБД работает,
на другой молча не работает, а интерфейс один и тот же.

## Требования назначения функциональности не действуют до применения

«Требования назначения функциональности начнут работать только после того
момента, как будет выполнена операция применения. До момента применения,
список требований, редактируемый в консоли кластера, не оказывает влияния
на работу кластера серверов» (§5.2.5.3).

Консоль показывает список так, будто он в силе. **Доказательством служит
факт вызова «Применить требования», а не вид списка.**

**А само применение может уронить всех:** «При выполнении операции полного
применения могут аварийно завершиться все клиентские приложения,
подключенные к кластеру серверов, на котором выполняется операция».

**Приоритет — это номер в списке:** «Чем меньше номер, тем раньше будет
обрабатываться требование (тем выше приоритет)», и меняется он командами
повышения и понижения, а не перетаскиванием.

## Две операции, которые рвут всё

**Удаление кластера:** «Внимание! Удаление кластера серверов приведет
к тому, что будут аварийно завершены все соединения с удаляемым кластером»
(§5.2.5.4). Отдельного подтверждения источник не описывает.

**Удаление рабочего сервера** тоже «может привести к аварийному завершению
клиентских соединений», и источник даёт способ этого избежать: заранее
добавить удаляемому серверу требование с максимальным приоритетом «Тип
объекта: Любой объект требования. Тип требования: Не назначать», применить
набор, дождаться разрыва соединений — и только потом удалять.

**Порядок здесь и есть содержание правила.** Без него операция необратима
для тех, кто работал.

## Удаление базы исполняется наполовину

Вариант «Удалить базу данных» при живых соединениях снимает регистрацию
в кластере, а сама база данных остаётся: сервер баз данных выполнить
удаление не сможет.

Итог — база исчезла из консоли и осталась на СУБД. Внешне это выглядит
как успешное удаление.

## Чего в §5.2 нет

- **что делать, если соединение на PostgreSQL всё-таки надо разорвать** —
  источник констатирует невозможность и способа не даёт;
- **как узнать, применены ли требования**, кроме памяти того, кто нажимал;
- **подтверждений у разрушительных команд:** удаление кластера описано
  предупреждением в тексте, а не диалогом.
