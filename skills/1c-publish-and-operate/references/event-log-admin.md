# Журнал регистрации: настройка, состав событий и две необратимые операции

**Ищут по словам:** настройка журнала регистрации, уровни важности,
разделение по периодам, сокращение журнала, `/ReduceEventLogSize`, формат
`.lgf` и `.lgd`, конвертация формата, событие «Доступ», «Отказ в доступе»,
аудит прав доступа, `ЗаписьЖурналаРегистрации`, отключить событие.

Источники: руководство разработчика, глава 22 (кроме §22.6); руководство
администратора, §6.13 и §7.4.11.

**Как достать факт из журнала** — у соседа `1c-quality-gates`
(`event-log-as-evidence.md`). Здесь другое: как журнал настроен, что в него
попадает и что теряется навсегда.

## Две необратимые операции

**Сокращение без архива.** «Если требуется сохранить удаляемые записи,
то нужно установить флажок Записать удаляемые записи в файл и указать имя
файла-архива» (§6.13.5.2). Флажок не взведён — записи не восстановить ничем:
журнал «не хранится в базе данных и не сохраняется при операциях
загрузки/выгрузки информационной базы», значит в резервной копии базы его
тоже нет.

Пакетный вариант той же операции — `/ReduceEventLogSize` с необязательным
`-saveAs`. **Необязательный параметр здесь и есть предохранитель.**

**Смена формата в одну сторону.** «После того, как формат журнала
регистрации успешно изменен на последовательный, файл журнала регистрации
в формате SQLite удаляется», и обратная конвертация не поддерживается.
Плюс предупреждение: «Внимание! Изменение формата журнала регистрации
занимает существенное время».

**И формат переживает выгрузку базы:** он сохраняется при смене во время
работы системы, то есть старая выгрузка вернёт базу с прежним форматом.

## Настройка применяется не тогда, когда её сохранили

Про события «Доступ» и «Отказ в доступе»: «Изменять настройки регистрации
следует при включенном монопольном режиме» — и главное, изменение
«гарантированно применяется только после перезапуска всех активных сеансов
данной информационной базы» (§22.4.1).

Вызов прошёл, ошибки нет, а старые сеансы пишут по-прежнему. **Включение
аудита не считается выполненным, пока сеансы не перезапущены** — и это
единственный способ узнать, что оно вообще включилось.

## Включённое событие без полей доступа не пишется вовсе

Таблица §22.4.2 даёт четыре строки, и вторая — ловушка: «Использование Поля
доступа Поля регистрации Результат Не задано Событие не регистрируется
Задано Не заданы Не заданы Событие не регистрируется Задано Заданы Не заданы
Событие регистрируется без детализации».

То есть **поля доступа — это триггер, а поля регистрации — содержимое.**
Галка «использовать» стоит, полей доступа нет — журнал пуст, и выглядит это
как «доступа не было».

## Что выключить нельзя

«Примечание. События, связанные с транзакциями (_$Transaction$_.Begin,
_$Transaction$_.Commit, _$Transaction$_.Rollback), не могут быть отключены»
методом управления регистрацией (§22.4.1).

Самый массовый источник записей рычагом выключения не глушится — только
разделением файлов и сокращением.

## Умолчания новой базы

«При создании новой информационной базы для журнала устанавливается режим
регистрации событий всех уровней важности» (§6.13.5.1), а «Журнал
регистрации, по умолчанию, хранится с разбиением по неделям».

Оба умолчания щедрые: пишется всё, а новый файл открывается раз в неделю.
На нагруженной базе это даёт большие файлы — источник рядом рекомендует
выбирать интервал так, чтобы файл оставался умеренным.

## Собственные события: три ограничения, о которых узнают поздно

«Количество уникальных имен пользовательских событий рекомендуется
ограничить 1 000 уникальных имен», и «Имена пользовательских событий должны
быть фиксированными строками, без включения в состав имен событий каких-либо
переменных данных».

**Содержимое кладут не в имя:** «Содержательную часть записываемого события
следует разместить в параметр Комментарий метода ЗаписьЖурналаРегистрации».

**И системное событие своим кодом не записать:** «Примечание. С помощью
данного метода невозможно записать в журнал регистрации системные события».

Имя с подставленным номером документа — типовая ошибка: тысяча уникальных
имён набирается быстро, и после этого журнал становится непригоден
для отбора.

## Аудит прав доступа — только КОРП, и он дорог

Раздел про события аудита открывается врезкой «Примечание. Доступно только
для лицензии КОРП», и подготовка данных для этих событий занимает заметное
время.

**И одна потеря, названная прямо:** событие изменения роли не сохраняет
прежний текст ограничения доступа — «Информации о содержимом ограничения
доступа к данным, которое было до выполнения изменения, не предоставляется».
То есть по журналу видно, что RLS меняли, и не видно, на что.

## Чего в главе 22 и §6.13 нет

- **полного перечня системных имён событий** — источник даёт только примеры
  (`_$Transaction$_.*`, `_$Access$_.Access`, `_$InfoBase$_.*`);
- **переносятся ли настройки детализации и состава событий при выгрузке
  базы** — про перенос формата сказано, про настройки нет;
- **что происходит с существующими файлами при смене периода разделения
  на ходу.**
