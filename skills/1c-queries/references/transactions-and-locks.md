# Транзакции, блокировки, запись данных

Всё ниже — по стандартам разработки 1С, с номером у каждого требования.
Это область, где стандарты 1С обобщают сильнее всего: они дают правила
безопасного поведения, а не описание того, как ведёт себя конкретная СУБД.

## Транзакции

Стандарт 783. Три особенности платформы, из которых следует всё остальное:

- **вложенные транзакции не поддерживаются**;
- **при исключении транзакция в общем случае не может быть зафиксирована** —
  и неважно, было исключение обработано или нет;
- транзакция начинается не только явно через `НачатьТранзакцию`: платформа
  начинает её неявно **при любой записи в базу данных**.

### Двадцать секунд — чужой таймаут, а не пожелание

Если две транзакции пересекаются по блокируемым ресурсам, начавшаяся позже
ждёт возможности установить блокировку ограниченное время — **по умолчанию
20 секунд**, — после чего завершается исключением «Превышено время ожидания
установки блокировки» (стандарт 783).

Отсюда и ориентир на длительность собственной транзакции: она измеряется
не терпением своего пользователя, а тем, сколько выдержит вставший за ней
в очередь. Стандарт приводит и рецепт для заведомо длинных операций: разбить
на порции так, чтобы запись порции в одной транзакции не превышала 20 секунд
в условиях высоконагруженной системы, и предусмотреть откат к предыдущей
версии при ошибке.

Возникновение таких исключений стандарт называет поводом провести анализ,
а не увеличить таймаут.

## Управляемый режим блокировки

Стандарт 460. В конфигурациях следует использовать **управляемый** режим
(свойство конфигурации «Режим управления блокировкой данных»).

Особенности, которые он же перечисляет:

- чтение данных другими транзакциями станет невозможным **только** если
  в текущей и других транзакциях устанавливаются несовместимые управляемые
  блокировки;
- **явная управляемая блокировка ставится перед чтением** в двух случаях:
  считываемое будет затем изменено, либо нужно обеспечить неизменность
  считанного до конца транзакции;
- блокировать следует **только те записи, которые действительно будут
  обработаны** кодом;
- **`ДЛЯ ИЗМЕНЕНИЯ` применять не следует** — стандарт называет конструкцию
  не имеющей смысла в этом режиме.

## Ответственное чтение

Стандарт 648. **Ответственным считается любое чтение, на основе результатов
которого производятся изменения в базе или принимаются решения.**

Такое чтение выполняется в транзакции с предварительной установкой управляемых
блокировок. Первый пример самого стандарта — чтение данных при проведении для
последующего формирования движений.

Определение важнее перечня: «ответственное» задано признаком, а не списком
мест, и новый случай, не названный в стандарте, тоже подпадает.

## Объектная блокировка

Стандарт 490. Главное требование стандарта: **прежде чем изменять существующий
объект информационной базы из кода, его следует предварительно заблокировать.**
Стандарт 648 повторяет это примечанием: перед модификацией ссылочных объектов
обычно следует устанавливать на них пессимистичные объектные блокировки.

**Но гарантии от чужой записи это не даёт, и путать нельзя.** Стандарт 490
говорит прямо: блокировка данных для редактирования **не запрещает запись**
заблокированных данных в других пользовательских сеансах (или в других
экземплярах объекта в том же сеансе), а лишь **не позволяет нескольким объектам
одновременно установить блокировку одних и тех же данных**. Формулировка
самого стандарта — «**попытаться** предотвратить изменение другими сеансами».

Прочитать её как «объект защищён» — значит получить потерю изменения: чужая
запись пройдёт, своя ляжет поверх, исключения не будет.

Это **не то же самое**, что управляемая (транзакционная) блокировка,
и одно другого не заменяет.

Стандарт называет и случаи, когда проверку можно не делать: монопольный режим,
приоритетные операции вроде загрузки при обмене.

## Где берутся массовые ожидания

Стандарт 659 даёт единственную причину: ожидание возникает, когда две сессии
захватывают **один и тот же «ресурс»** — неделимую единицу данных. Всё
остальное — частные случаи, и смотреть надо на структуру метаданных.

Стандарт называет три объекта метаданных, на которые следует обратить внимание
при анализе структуры: **`Последовательность`**, **регистры бухгалтерии**,
**регистры накопления**. `Последовательность` здесь — самостоятельный объект
метаданных, а не свойство справочника; именно её разбирает стандарт 662.

Готового чек-листа с числами стандарт не даёт — и это честно: числа зависят
от нагрузки.

### Контроль остатков

Стандарт 661. Контроль остатков при проведении требует **блокирующего** чтения
итогов: два пользователя не должны одновременно читать один и тот же остаток
за период, счёт и значение измерения.

Стандарт разбирает последствие буквально: оба прочитали 10 единиц, первый
списал 8 (можно), второй списал 6 (тоже можно) — итог минус 4, что прикладной
логикой недопустимо.

Порядок, который стандарт предлагает вместо этого, различает **две группы
регистров**, и у них противоположные настройки. Слить их в одну — потерять
весь приём.

**Шаг 1. В начале транзакции — регистры, которые контроля остатков
не требуют.** У всех записываемых регистров накопления и бухгалтерии
**включён разделитель итогов**, а у наборов записей свойство
`БлокироватьДляИзменения` установлено в **`Ложь`**. Порядок записи регистров
всегда одинаковый — например алфавитный.

**Шаг 2.** Все остальные действия транзакции.

**Шаг 3. В самом конце транзакции — явно записать движения по регистрам,
которые контроля требуют.** У наборов записей этих регистров
`БлокироватьДляИзменения` установлено в **`Истина`**. Стандарт называет
причину прямо: **это необходимо для предотвращения взаимоблокировки.**

**Шаг 4. Запрос контроля остатков по каждому регистру.** Он должен считывать
**только отрицательные** остатки по заданному набору значений измерений,
а не все.

Явная управляемая блокировка на четвёртом шаге не нужна — но **только потому,
что её роль уже сыграл `БлокироватьДляИзменения = Истина` на третьем**.
Стандарт связывает это словами «в этом случае»: именно при этом свойстве
запись набора устанавливает блокировку остатков регистра по данному набору
значений измерений.

Снять явную блокировку, не поставив свойство, — значит читать контрольным
запросом незаблокированные остатки, то есть получить ровно тот минус, ради
которого приём и затевался. Ошибка в обратную сторону, в первой группе
регистров, даёт взаимоблокировку.

Отсюда общее правило расположения: всё, что не требует контроля, записывается
раньше, а сам контроль сдвигается ближе к концу транзакции.

### Граница последовательности

Стандарт 662. Сдвиг границы последовательности при оперативном проведении
делает общим ресурсом блокировки **все документы с одинаковым набором значений
измерений последовательности** — отсюда массовые ожидания.

Типовое следствие, которое называет сам стандарт, — перенести операцию
в регламентное задание.

### Разделение итогов

Два стандарта, и у них разные первые средства. Перепутать порядок — значит
крутить переключатель вместо того, чтобы починить структуру.

**Регистры накопления (стандарт 664) — сначала состав измерений.** Остатки
по одному набору измерений хранятся в одном ресурсе регистра, поэтому степень
параллельности **фактически задаётся составом измерений**; его подбирают под
то, насколько мелко должны быть «нарезаны» остатки, исходя из прикладной
функциональности. И только **если состав измерений не позволяет обеспечить
необходимую параллельность**, стандарт рекомендует включать режим разделения
итогов — «аналогично регистрам бухгалтерии».

**Регистры бухгалтерии (стандарт 663) — сразу разделение итогов.** При
оперативной многопользовательской записи движений режим рекомендуется включать:
с ним пользователи параллельно обновляют таблицу остатков даже когда совпадают
**период, счёт и значения измерений**. Без него таблица остатков становится
узким местом при конкурентной работе большого числа пользователей.

### Два органа управления, а не один

Стандарт 663 в собственном примере делает это **в два шага**, и шаги живут
в разных режимах:

> «Разрешим режим разделения итогов (**в режиме конфигурирования**)»
> «Включим режим разделения итогов (**в режиме 1С:Предприятия**)»

Руководство разработчика, глава 5, объясняет почему: режим требует
дополнительных расходов ресурсов — «увеличивается количество данных в итоговых
таблицах», — «поэтому свойства есть **и в конфигурации, и в языке** для
управления этим режимом». Там же сказано, что режим «может быть изменён
пользователем в режиме работы 1С:Предприятие» и по умолчанию включён.

**Разрешение — свойство конфигуратора, то есть изменение конфигурации рабочей
базы и решение владельца.** Включение — переключатель времени выполнения.
Прочитать вторую половину как весь механизм значит выдать себе разрешение,
которого никто не давал.

Записи при включённом режиме «размножаются» только при параллельно
выполняемых транзакциях, а их число по каждой комбинации измерений зависит
от максимального числа одновременных транзакций; при пересчёте итогов
накопленные отдельные записи сворачиваются.

Две оговорки, обе из самих стандартов:

- режим **не спасает при контроле остатков** — тогда контроль переносят
  ближе к концу транзакции (стандарт 663 прямо ссылается на стандарт 661);
- включённое разделение итогов **мешает самому быстрому чтению остатков**:
  стандарт 733 требует, чтобы разделение итогов было выключено, — это одно
  из трёх условий, при которых платформа читает хранимую таблицу текущих
  остатков без группировки по измерениям.

Один и тот же переключатель ускоряет запись и замедляет самое быстрое чтение
остатков. Однозначного правила «что важнее» ни один из трёх стандартов
не даёт, и выбор делается по профилю нагрузки конкретной системы.

### Разрешение итогов для периодических регистров сведений

Стандарт 708 — методическая рекомендация. Разрешать итоги стоит, когда
выполнены **все** условия сразу:

- в регистре ожидается **большой объём данных** (оправданно для цен
  номенклатуры, бессмысленно для курсов валют);
- в конфигурации есть **частотные запросы к срезам последних или первых
  на текущий момент** — то есть период в параметрах виртуальных таблиц
  `СрезПоследних` и `СрезПервых` не задан;
- остальные условия этих виртуальных таблиц задаются **только на значения
  измерений** (и разделителей в режиме «Независимо и совместно»).

Если запросы всегда идут на конкретную дату либо отбор среза делается
подзапросами и соединениями через точку, эффекта не будет.

## Чтение отдельных реквизитов

Стандарт 496. Обращение к реквизиту через точку от ссылки и вызов
`ПолучитьОбъект()` читают из базы **весь объект целиком, вместе с табличными
частями**. Для чтения нескольких отдельных реквизитов нужен запрос.

Стандарт называет и готовую функцию из состава библиотеки стандартных
подсистем. Этот набор про БСП правил не даёт — она вне его охвата, — поэтому
здесь она названа как существующая альтернатива, а не как способ, на который
можно опереться в конфигурации без библиотеки.

## Запись наборов записей

Стандарт 792.

**1. Не записывать наборы в цикле по одной или нескольким записям** — это
в несколько раз медленнее записи одним набором. Ориентир — порции по
**1000 записей**.

**2. Не перезаписывать большой набор, если меняется не более 30% записей.**
Перезапись удаляет все записи по отбору и вставляет все новые, включая
неизменившиеся; вдобавок избыточно растёт журнал транзакций СУБД —
пропорционально числу удалений и вставок. Вместо этого записываются
только изменения.

**3. Режимы замещения в сочетании с вычислением изменённых записей.**
Частный случай — добавление в пустой регистр: достаточно задать параметру
`РежимЗамещения` метода `Записать` значение `Ложь`. В остальных случаях
стандарт называет режимы **Слияние**, **Удаление** (с версии платформы
8.3.26) и **Обновление** (с версии 8.3.27) — они обрабатывают записи
пакетно, порциями.

Оговорка о версиях здесь существенна: набор рассчитан на платформу 8.3 любой
подверсии, и два из трёх режимов на более ранних подверсиях недоступны.

## История работы пользователя

Стандарт 497. Интерактивные изменения объектов платформа фиксирует сама;
объект `ИсторияРаботыПользователя` вызывается **дополнительно** — когда
действие пользователя нужно зарегистрировать сверх этого.

## Менеджер записи или набор записей (стандарт 447)

Область применения — «управляемое приложение, мобильное приложение, обычное
приложение».

**Чтение — запросом** (пункт 1): «Чтение записи (набора записей) из регистра
сведений **без последующей модификации необходимо выполнять запросом**». Это
та же мысль, что и у стандарта 496 про реквизиты объекта, но для регистра
сведений.

**Менеджер записи — только для одного случая** (пункт 2): «Объект
`РегистрСведенийМенеджерЗаписи` **следует применять только тогда**, когда
выполнение операций с регистром сведений **требует использования отбора
одновременно по всем измерениям**».

И механика оттуда же, неочевидная: «менеджер записи использует для выполнения
записи **два набора записей**, устанавливая им соответствующие значения
отборов. Поэтому **обработчики событий набора записей вызываются и тогда**,
когда для записи данных используется менеджер записи».

**Во всех остальных — набор записей** (пункт 3): «следует использовать объект
`РегистрСведенийНаборЗаписей`. С точки зрения производительности использование
менеджера записей в некоторых случаях будет **столь же эффективным**, как
и использование набора записей, а в некоторых — **менее**, так как будут
выполняться лишние действия».

Пример источника — тот же класс, что и «писать набором, а не по записи»
из стандарта 792:

```bsl
// Правильно — один набор на всю таблицу:
Набор = РегистрыСведений.ЗначенияПравПользователя.СоздатьНаборЗаписей();
Набор.Отбор.НаборПрав.Установить(ЗначениеНабораПрав);
Для Каждого СтрокаТаблицы Из ТаблицаЗначенийПрав Цикл
	Запись = Набор.Добавить();
	Запись.НаборПрав = ЗначениеНабораПрав;
	Запись.Право = СтрокаТаблицы.Право;
	Запись.Значение = СтрокаТаблицы.Значение;
КонецЦикла;
Набор.Записать();

// Неправильно — менеджер записи в цикле:
Для Каждого СтрокаТаблицы Из ТаблицаЗначенийПрав Цикл
	ЭлементРегистраСведений = РегистрыСведений.ЗначенияПравПользователя.СоздатьМенеджерЗаписи();
	// …
	ЭлементРегистраСведений.Записать();
КонецЦикла;
```
