# Проверки, которые платформа делает только по ключу запуска

**Ищут по словам:** `/EnableCheckModal`,
`/EnableCheckExtensionsAndAddInsSyncCalls`, `/EnableCheckServerCalls`, строгая
проверка модальности, проверка синхронных вызовов, контекстный серверный вызов
в обработчике, `ПередЗаписью` и серверный вызов, диагностика во время
исполнения, информация для технической поддержки.

Источники: руководство администратора, приложение 7 §7.3.9 «Проверки во время
работы клиентского приложения»; руководство разработчика — глава 5 (свойство
«Режим использования модальности» и поведение клиентов), глава 4
(`/EnableCheckServerCalls`), глава 35 (создание обработчика), глава 39
(настройки запуска из конфигуратора); `std636`, `std703`.

**Это третий прибор, и он отдельный.** Статическая проверка читает текст
(см. `config-check.md`), автотест воспроизводит сценарий (`autotest.md`),
а эти ключи заставляют платформу ругаться **во время работы** на то, что
иначе проходит молча.

## Три ключа

«7.3.9. Проверки во время работы клиентского приложения
/EnableCheckModal Включает режим строгой проверки использования модальных
методов… /EnableCheckExtensionsAndAddInsSyncCalls Включает режим строгой
проверки использования синхронных вызовов расширений работы с файлами
и криптографией и внешних компонент. **Игнорируется при запуске толстого
клиента.**» (приложение 7, §7.3.9).

Последняя фраза относится ко второму ключу и стоит того, чтобы её заметить:
под толстым клиентом он даёт заведомо зелёный результат.

Третий описан в руководстве разработчика: «Если в командной строке запуска
клиентского приложения присутствует ключ /EnableCheckServerCalls…,
то при обнаружении нарушения указанных правил, в окно сообщений выводится
диагностика. Эта же диагностика будет присутствовать в диалоге Информация
для технической поддержки».

## Свойство отвечает за компиляцию, ключ — за поведение на бою

Самое дорогое здесь: «Описанное выше поведение (только для толстого и тонкого
клиентских приложений) будет наблюдаться только при использовании параметра
/EnableCheckModal командной строки запуска системы. Если этот параметр
не указан, то модальные методы сохраняются работоспособность вне зависимости
от свойства конфигурации Режим использования модальности» (орфография
источника).

То есть **на тонком и толстом клиенте свойство само по себе не мешает
модальному методу отработать.** Запрет во время работы включается ключом,
а обычный ярлык пользователя его не несёт.

**Но статическая проверка при этом не нема — если свойство выставлено
жёстко.** «Если свойство имеет значение Не использовать ‑ модальные окно
нельзя использовать в данном прикладном решении. При попытке использования
методов будет диагностироваться ошибка (в том числе и при синтаксическом
контроле текста на встроенном языке)» (орфография источника).

Значит различать надо два разных вопроса:

- **компилируется ли** — при значении «Не использовать» модальный метод
  ловится синтаксическим контролем, без всякой расширенной проверки;
- **сработает ли на бою** — вот это без ключа не проверяется: «модальные
  методы сохраняются работоспособность вне зависимости от свойства».

А при значении «Использовать с предупреждением» «ошибки диагностироваться
не бу…» дут — и тогда молчит уже и статика.

## Зачем вообще ключ, если есть статическая проверка

Потому что нарушение проявляется не всегда: «Нарушение этого запрета может
приводить к ошибкам не во всех случаях использования серверных вызовов.
В основном проблемы возникают, если в таком обработчике в серверном вызове
изменяются элементы формы или ее реквизиты. В результате может наблюдаться
неожиданное поведение или неочевидные ошибки времени исполнения».

Ошибка, которая случается через раз, статической проверкой не ловится
и в отчёте о тестировании выглядит как «не воспроизводится».

## Что читать в коде, если запустить нельзя

`std636`, п. 2.1: «в некоторых клиентских обработчиках событий форм
(ПередЗаписью, ПослеЗаписи, ПередЗакрытием, ПриЗакрытии и др.) не допускается
вызов контекстных серверных процедур, а также выполнение действий, которые
могут привести к неявному серверному вызову».

**«И др.» — прямое признание, что перечень неполон.** Полного списка нет
ни в стандарте, ни в руководстве: он размазан по описаниям событий
в синтакс-помощнике. Поэтому чтение кода даёт **нижнюю** оценку числа
нарушений, а верхнюю — только запуск с ключом.

## Профилактика в конфигураторе есть, но дырявая

«Если в каком либо клиентском обработчике события не рекомендуется
использовать контекстные серверные вызовы (информация об этом доступа
в Синтакс-помощнике), то использование последнего варианта (с контекстной
серверной процедурой) недоступно» (орфография и опечатка источника).

Это единственная встроенная профилактика — снятый пункт в диалоге создания
обработчика. Она не срабатывает, когда процедура написана руками, скопирована
из другого модуля или пришла из расширения.

**Вывод для приёмки:** отсутствие ошибок при разработке не значит, что
нарушений нет; значит только, что мастером их не создавали.

## Как это ставится из конфигуратора

Флажок «Проверять серверные вызовы в обработчиках событий» в настройках
запуска добавляет `/EnableCheckServerCalls` в командную строку. То есть
у прибора два входа — флажок в конфигураторе и ключ в ярлыке, — и результат
у них один, а видимость разная: **из чужого ярлыка ключ не виден никому.**

## Чего здесь нет

- **машинного вывода:** диагностика идёт в окно сообщений и в «Информацию
  для технической поддержки», файла отчёта у неё нет;
- **полного перечня обработчиков**, где контекстный серверный вызов запрещён;
- **поведения веб-клиента:** ключи описаны для клиентского приложения,
  а веб-клиент ведёт себя иначе (см. главу 4 руководства разработчика).
