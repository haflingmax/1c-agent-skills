# Проверка в конвейере: чем доказывается, что она была

**Ищут по словам:** `/CheckModules`, `/CheckConfig` в пакетном режиме, `/Out`,
`/DumpResult`, код возврата конфигуратора, `-NoTruncate`, `/Visible`,
`/DisableStartupMessages`, ворота качества в CI, служебные сообщения,
`/IBRestoreIntegrity`.

Источник: руководство администратора, приложение 7 «Параметры командной
строки» (§7.3.11, §7.4.3, §7.4.5, §7.4.17).

Перечень ключей как справочник — у соседа `1c-build-and-db`. Здесь другое:
**какой вызов доказывает, что проверка выполнена, а какой только выглядит
так.**

## Голый `/CheckModules` не проверяет ничего

«Должен быть указан один или несколько параметров, описывающих режимы
проверки. Если параметры не указаны, проверка выполнена не будет»
(приложение 7, §7.4.5).

Команда отработает, не пожалуется и завершится. В скрипте приёмки это даёт
зелёный результат при нулевом покрытии.

Отсюда правило разбора чужого конвейера: **проверять надо не факт запуска,
а наличие хотя бы одного режима в командной строке.** Вот вызов, который
выглядит воротами и ими не является:

```
1cv8 DESIGNER /IBName база /DisableStartupDialogs /CheckModules
```

Он завершится успешно и не проверит ни одного модуля.

## Без `/Out` находки некуда деть

«/Out <имя файла> [-NoTruncate] Установка файла для вывода служебных
сообщений… В пакетном режиме запуска запись сообщений в файл
не буферизуется (сообщения записываются сразу). Файл формируется в кодировке
UTF-8» (§7.3.11).

Все находки `/CheckConfig` и `/CheckModules` — это служебные сообщения.
Без `/Out` они не попадают никуда, и прогон выглядит успешным.

Две мелочи, которые стоят часа: файл **UTF-8** (читать его в консоли
с кодовой страницей 866 бесполезно), и по умолчанию он **очищается** —
`-NoTruncate` нужен, если в один файл пишут несколько шагов.

## Признак успеха запрашивается отдельно

«/DumpResult <имя файла> Записать результат работы конфигуратора в файл.
Результат ‑ число (0 ‑ в случае успеха)» (§7.4.17).

Машиночитаемый признак у пакетного конфигуратора — **отдельная команда,
а не код возврата процесса.** Ворота, построенные на «процесс завершился —
значит прошло», не отличают проверку без ошибок от проверки, которой
не было.

## Коды возврата описаны ровно у одной проверочной команды

`/IBRestoreIntegrity`: «Восстановление информационной базы не требуется…
Код возврата в этом случае равен 0. ● Информационная база успешно
восстановлена… Код возврата в этом случае равен 0. ● Если в процессе попытки
восстановления произошла любая ошибка ‑ текст ошибки будет помещен в файл
и код возврата в этом случае равен 1» (§7.4.3).

Для `/CheckConfig`, `/CheckModules` и `/IBCheckAndRepair` такого описания
в приложении 7 нет. **Считать их код возврата признаком «проверка пройдена»
источник не разрешает** — для них признак берётся из `/DumpResult` и `/Out`.

**И там же оговорка про лишние параметры:** «При обнаружении других
параметров они будут игнорироваться». Опечатка в имени ключа не ошибка —
ключ просто выброшен, и прогон идёт дальше как ни в чём не бывало. Это тот
же класс, что и `/CheckModules` без режимов: команда сделала меньше, чем
написано, и промолчала.

## Два ключа, без которых пакетный прогон висит

**`/Visible`** — пакетная команда по умолчанию невидима, и окно, которого
никто не видит, ждёт нажатия так же терпеливо.

**`/DisableStartupMessages`** глушит стартовые сообщения, которые иначе
останавливают прогон в ожидании человека.

К ним же — `/DisableUnrecoverableErrorMessage` из соседнего справочника
`runtime-errors.md`: без него невосстановимая ошибка показывает окно
и прогон не кончается никогда.

## Что из этого складывается

Вызов, который действительно является воротами, называет три вещи: **режимы
проверки** (иначе она не выполнится), **файл сообщений** (иначе находки
пропадут) и **файл результата** (иначе успех не отличить от бездействия):

```
1cv8 DESIGNER /IBName база /DisableStartupDialogs /CheckModules -ThinClient -Server /Out check.log /DumpResult result.txt
```

Всё, чего в вызове нет, не проверено — и в отчёте это ничем не отмечено.
Режимы здесь названы для примера: их состав берётся из режимов запуска
самой конфигурации, а не из привычки.

## Чего в приложении 7 нет

- **кодов возврата у проверочных команд** — кроме `/IBRestoreIntegrity`;
- **формата файла сообщений:** он текстовый и человеческий, разбирать его
  приходится своими средствами;
- **способа узнать, какие режимы проверки прогонялись**, из самого файла
  результата: это знает только тот, кто писал командную строку.
