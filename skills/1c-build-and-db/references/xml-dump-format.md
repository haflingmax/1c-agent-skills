## Два похожих механизма, которые путают

Глава 2 описывает два разных механизма, и имена ключей у них отличаются
одним словом.

| Механизм | Что делает | Ключи |
|---|---|---|
| §2.16 «Выгрузка и загрузка файлов конфигурации» | выборочно выгружает **отдельные свойства** объектов: модули, макеты, справку, права | `/DumpConfigFiles`, `/LoadConfigFiles` |
| §2.17 «Выгрузка и загрузка конфигурации в файлы» | выгружает **все объекты конфигурации** в xml-файлы и грузит обратно | `/DumpConfigToFiles`, `/LoadConfigFromFiles` |

Исходники, которые правят руками и держат в системе контроля версий, — это
§2.17, и весь этот файл про него. Про §2.16 достаточно знать состав
расширений, потому что по ним механизм и узнаётся: `htm` — справка и макеты
HTML-документа, `txt` — модули и макеты текстового документа, `mxl` — макеты
табличного документа, `geo` — географические схемы, `grs` — графические
схемы, `bin` — двоичные макеты. Картинки выгружаются в том формате, в
котором хранятся в конфигурации. Права выгружаются в XML и включают сами
права, ограничения доступа к данным и шаблоны ограничений. Справка и макеты
HTML дают отдельный файл на каждый язык, код языка стоит перед расширением:
`Документ.РасходТовара.Справка.ru.htm`. Если при загрузке найден один файл
без кода языка, он грузится для текущего языка конфигурации.

Что полезно знать про §2.17 до всякого формата (2.17.1):

- Ссылки на **отсутствующие** объекты конфигурации выгружаются текстовым
  представлением идентификатора и при загрузке восстанавливаются в ссылку
  на отсутствующий объект — ради идентичности двух конфигураций.
- Для реквизитов и элементов управляемой формы выгружаются внутренние
  идентификаторы: ими, в частности, сохраняются и восстанавливаются настройки.
- У ролей выгружаются значения только тех прав, которые на момент выгрузки
  отличаются от значений по умолчанию; умолчания задают свойства роли
  «Устанавливать права для новых объектов» и «Устанавливать права для
  реквизитов и табличных частей по умолчанию».
- Расширение выгружается и загружается тем же механизмом; выгружаются
  расширенные или контролируемые свойства.
- Если при загрузке в файлах найдены ошибки, платформа показывает окно со
  списком; некритичные можно принять, а по строке — открыть файл с ошибкой.

Правила, из которых эта таблица только следствие:

- Явное указание номера версии в самих файлах выгрузки начинается с версии
  2.0, то есть с платформы 8.3.7. **Если номера версии в файлах нет, выгрузка
  считается версией 1.0** — отсутствие номера не означает «версия любая».
- Версия едина для всех объектов конфигурации, которые могут быть выгружены
  в файлы. Она записывается в корневые XML-файлы объектов конфигурации и в
  корневые XML-файлы некоторых подчинённых объектов. Файлы выгрузки, чей
  формат не XML, указания на версию внутри себя не содержат.
- **Выгрузка всегда выполняется в формате текущей версии платформы** — той,
  из которой выгружают. Выбрать версию формата при выгрузке нельзя.
- **Загрузка проходит, только если версия загружаемых файлов меньше или
  равна версии платформы**, которой грузят. Файлы более новой версии
  платформа постарше не примет.

Отсюда практический вывод: проставить в исходниках версию «на будущее»
нечем и незачем — выгрузка перепишет её своей, а загрузка на платформе
постарше откажет. Если файлы нужны платформе постарше, выгружать надо ею же.

## Иерархический формат

Формат по умолчанию и единственный, который доступен из конфигуратора
(2.17.3.1, 2.17.4). Все файлы и каталоги создаются внутри каталога,
указанного при выгрузке, — он называется корневым каталогом выгрузки.

- Путь к корневому каталогу рекомендуется держать короче 30 символов: это
  уменьшает вероятность прерывания выгрузки из-за превышения длины пути к
  выгружаемому файлу.
- Объекты лежат в подкаталогах по своим типам: справочники в `Catalogs`,
  документы в `Documents` и так далее. Объекты ветки «Общие» тоже уходят в
  «свои» подкаталоги корневого каталога, без промежуточного подкаталога.
- Свойства самой конфигурации — в файле `Configuration.xml` непосредственно
  в корневом каталоге выгрузки.

Каждый объект выгружается так:

- Описание объекта — в xml-файл с именем объекта. Если у объекта есть
  подчинённые объекты (реквизиты, команды, формы), рядом создаётся
  подкаталог с тем же именем.
- В подкаталоге объекта заводятся подкаталоги для групп подчинённых
  объектов — **кроме реквизитов и табличных частей: они лежат в самом
  xml-файле объекта**. Отдельными подкаталогами выносятся: `Forms` — формы,
  `Commands` — команды, `Templates` — макеты, `Cubes` — кубы внешнего
  источника данных, `Tables` — таблицы внешнего источника данных.
- Остальные свойства объекта (и самой конфигурации) размещаются в
  подкаталогах `Ext` разного уровня подчинения.
- Подчинённый объект с иерархической структурой выгружается так же, как
  родительский объект конфигурации.

Что лежит в `Ext`:

| Уровень | Файлы |
|---|---|
| Сама конфигурация | `ManagedApplicationModule.bsl` — модуль управляемого приложения; `ExternalConnectionModule.bsl` — модуль внешнего соединения; `SessionModule.bsl` — модуль сеанса |
| Объект конфигурации | `ObjectModule.bsl` — модуль объекта; `CommandModule.bsl` — модуль команды; `ManagerModule.bsl` — модуль менеджера объекта; `RecordSetModule.bsl` — модуль набора записей; `ValueManagerModule.bsl` — модуль менеджера значения; `Predefined.xml` — предопределённые данные; `Schedule.xml` — расписание регламентного задания; `Rights.xml` — права роли; `Template.xml` — файл макета |
| Подчинённый объект | `Module.bsl` — модуль управляемой формы; `Form.xml` — описание управляемой формы; абсолютные картинки элементов формы |

Файлы, относящиеся к обычному приложению, здесь не разбираются: охват набора —
платформа 8.3 и управляемое приложение. В выгрузке они встречаются, и их
назначение смотри в самом руководстве.

Справка объекта: общее описание в `Help.xml`, файлы справки — в каталоге
`Help` с именами вида `<код языка>.html`; абсолютные картинки справки — в
подкаталоге `_files` каталога `Help`. Графическая схема или диаграмма
бизнес-процесса: описание в `Flowchart.xml`, графические элементы — в
каталоге `Flowchart`, в подкаталоге `Items`, где каждый элемент представлен
подкаталогом с картинкой внутри.

Три структуры, устроенные не так, как ожидается:

- **Форма.** Описание формы — в xml-файле с именем формы; рядом подкаталог
  с именем формы, в нём `Ext`, в `Ext` — `Form.xml` (описание собственно
  формы) и подкаталог `Form`, а уже в нём `Module.bsl` с модулем формы.
  Справка формы тоже лежит в `Ext`.
- **Макет.** Описание — в xml-файле с именем макета; рядом подкаталог с
  именем макета, в нём `Ext`, а в `Ext` — файл макета. **Имя файла зависит
  от значения `TemplateType` в описании**, и здесь руководство разработчика
  расходится с выгрузкой: гл. 2 §2.17.3.1 пишет «`Template.xml` — макет,
  помещённый как документ HTML… `Template.bin` — макеты во всех остальных
  форматах». Замер по выгрузкам (`_ref`, все пять типов, 24 макета) говорит
  иначе:

  | `TemplateType` | Файл |
  |---|---|
  | `TextDocument` | `Ext/Template.txt` |
  | `HTMLDocument` | `Ext/Template.html` |
  | `SpreadsheetDocument` | `Ext/Template.xml` |
  | `DataCompositionSchema` | `Ext/Template.xml` |
  | `BinaryData` | `Ext/Template.bin` |

  То есть из трёх строк руководства верна одна (`Template.txt`): HTML лежит
  в `.html`, а `.bin` достаётся только двоичным данным — табличный документ
  и схема компоновки идут в `.xml`. Корень у них разный:
  `<SpreadsheetDocument xmlns="http://v8.1c.ru/spreadsheet/document">`
  и `<DataCompositionSchema xmlns="http://v8.1c.ru/8.1/data-composition-system/schema">`.
  **Верить выгрузке**: расхождение проверено 26.08.2026 счётом типов
  и файлов, а не прочтением.
- **Внешние источники данных.** Источник — в xml-файле с именем источника,
  рядом подкаталог с тем же именем, в нём `Cubes` или `Tables`. Каждый куб —
  xml-файл с именем куба плюс подкаталог с `DimensionTables`, где лежат
  описания таблиц измерений. Каждая таблица внешнего источника выгружается
  как отдельный объект конфигурации.

**Подсистемы.** Выгружаются как обычный объект конфигурации, а подчинённые
подсистемы — в подкаталоге внутри каталога подсистемы. Имя этого подкаталога
напечатано в руководстве как `Sybsystems` — судя по соседней таблице
соответствия, где подсистемам отвечает `Subsystems`, это опечатка источника;
проверяй по фактической выгрузке своей платформы, а не по этой строке.
Руководство рекомендует не использовать более трёх вложенных подсистем,
считая подсистему верхнего уровня, чтобы не нарушить ограничение на полный
путь к файлам объектов подсистем (255 символов); если уровней нужно
больше — давать подсистемам максимально короткие имена.

## Линейный формат — устаревший

Руководство помечает его прямо: линейный формат устарел, его использование
не рекомендуется, автономный сервер с ним не работает, рекомендуется
иерархический (2.17.3.2). Из конфигуратора линейная выгрузка недоступна
вовсе — только пакетным режимом запуска (2.17.4).

Знать его состав нужно ровно для одного: опознать чужой каталог выгрузки и
не пытаться грузить его как иерархический. Признак — плоский список файлов
с точками в именах вместо дерева каталогов:

- Объекты конфигурации: `Document.ПродажиТоваров.xml`,
  `CommonPicture.ПодсистемаЗакупки.xml` (описание объекта, но не сама
  картинка). Отдельными файлами идут и подчинённые объекты, отдельно
  захватываемые в хранилище конфигурации.
- Отдельные свойства большого объёма или сложной структуры:
  `CommonPicture.ПодсистемаЗакупки.Picture.xml`,
  `DataProcessor.Путеводитель.Template.ГлавнаяСтраница.xml`.
- Значения свойств, являющиеся файлами известных форматов (не XML):
  `CommonPicture.ПодсистемаЗакупки.Picture.Picture.png`,
  `Catalog.Товары.Form.ФормаЭлемента.Form.Module.txt`.
- Модуль объекта — текстовым файлом, если он может быть получен, иначе в
  двоичном виде: `DataProcessor.ЖурналРегистрации.ObjectModule.txt`.
- HTML — набором файлов: корневой файл со списком страниц, страницы по
  языкам, картинки. Справка объекта — частный случай:
  `Catalog.Товары.Help.xml`, `Catalog.Товары.Help.ru.html`,
  `Catalog.Товары.Help.Картинка.png`.
- Конфигурации поставщиков: `Configuration.ParentConfigurations` — файл
  информации о них во внутреннем формате (не XML), плюс файл `.cf` на
  каждую конфигурацию поставщика.

Все ссылки на объекты метаданных, ссылки на поля и идентификаторы типов
выгружаются именами, и все идентификаторы — по-английски: `Catalog.Товары`,
а не `Справочник.Товары`. Названные руководством проблемы линейного
формата — сложность переноса каталога между файловыми системами и
неуникальность имён файлов выгружаемых объектов в ряде случаев.

## Configuration.xml и состав ChildObjects

`Configuration.xml` — основной файл выгрузки; он содержит описание свойств
собственно конфигурации и лежит в корневом каталоге выгрузки (2.17.1,
2.17.3.1, 2.17.4).

**Состава самого файла руководство в §2.16–2.17 не описывает.** Ни перечня
элементов внутри него, ни элемента `ChildObjects` со списком объектов
конфигурации там нет — сказано только, что файл содержит свойства
конфигурации. Поэтому имена и порядок элементов внутри `Configuration.xml`
берутся из фактической выгрузки той платформы, с которой работаешь, а не из
памяти: сделай `/DumpConfigToFiles` и посмотри, как оно устроено на самом
деле.

Что руководство про этот файл всё-таки говорит по делу — правило родителя
при частичной загрузке (2.17.5.3.2, 2.17.5.3.3): чтобы **добавить** объект,
грузят два файла — сам объект и его родителя; чтобы **удалить**, грузят файл
родителя, в котором информации об удаляемом объекте уже нет. Для объекта
верхнего уровня — справочника, документа, регистра — родителем является сама
конфигурация, а её файл и есть `Configuration.xml`. Прямым текстом
руководство эту связку не пишет: оно говорит «файл родительского объекта».
Отсюда и практика правки списка объектов в `Configuration.xml` — но её
результат доказывается загрузкой и повторной выгрузкой, а не чтением.

## Файл версий ConfigDumpInfo.xml

Кроме `Configuration.xml`, при выгрузке система формирует файл версий
`ConfigDumpInfo.xml` с именем объекта и его версией (2.17.4). Назначение у
этой информации ровно одно: при повторной выгрузке в тот же каталог
конфигуратор выгрузит только те объекты, версия которых отличается от
записанной в прошлый раз. «Версия» здесь — последовательность символов,
которая меняется, если объект редактировался.

Полная выгрузка вместо обновления случится, если:

- в каталоге выгрузки нет файла версий (тогда он и будет создан);
- переименована сама конфигурация;
- переименован или удалён объект конфигурации;
- изменены свойства `ПредопределенныеДанные` или `ДиаграммаБизнесПроцесса` —
  в конфигурации могут быть ссылки на элементы предопределённых данных и на
  точки бизнес-процесса, и эти изменения влияют на целостность выгрузки.

Формат выгрузки в выбранном каталоге обязан совпадать с форматом текущей
выгрузки: выгрузка в линейном формате поверх иерархического (и наоборот)
даёт ошибку, выгрузка не произойдёт.

Состав самого `ConfigDumpInfo.xml` в §2.17 не разобран — там на него дана
отдельная ссылка. При загрузке файл версий создаётся или обновляется
параметром `-updateConfigDumpInfo` (приложение 7, 7.4.4).

Ещё две возможности выгрузки оттуда же (2.17.4): выгружать не в каталог, а
в zip-архив — структура архива совпадает со структурой каталога выгрузки,
объём меньше и передавать быстрее; и выполнять выгрузку на сервере в
клиент-серверном варианте несколькими фоновыми заданиями, где количество
заданий 0 означает, что «платформа автоматически определит это количество,
исходя из параметров процессора на компьютере с кластером серверов
1С:Предприятия».

## Полная загрузка

Полная загрузка заменяет основную конфигурацию данными из файлов целиком и
на большой конфигурации занимает существенное время (2.17.5.2). Что можно
загрузить, а что нет:

| Состояние конфигурации | Полная загрузка |
|---|---|
| не на поддержке и не подключена к хранилищу | без ограничений |
| подключена к хранилищу конфигурации | **невозможна**, соответствующий пункт меню недоступен |
| на поддержке | только если включена возможность изменений и все объекты можно редактировать |

**Настройки поддержки при загрузке из XML платформа не проверяет**
(2.17.5.1). За их правильность отвечает человек, а загрузка неверных
настроек поддержки может сделать неработоспособным механизм обновления
конфигурации и саму конфигурацию. Это тот случай, когда «загрузилось без
ошибок» ничего не доказывает.

Команда полной загрузки — обычная:

```
1cv8 DESIGNER /F d:/base /LoadConfigFromFiles d:/src /UpdateDBCfg -Dynamic- /DisableStartupDialogs /Out d:/log/load.txt
```

## Частичная загрузка

Смысл — время: полная загрузка идёт долго, а меняются обычно немногие файлы
(2.17.5.3.1). Что важно знать до первой попытки:

- Частичная загрузка выполняется **только** ключом `/LoadConfigFromFiles`
  пакетного запуска конфигуратора; в интерактивном режиме её нет. Не
  поддерживается она и при работе с несколькими расширениями.
- Грузить можно как сам объект конфигурации, так и подчинённые объекты —
  формы, справку, модули. Если грузится объект, он грузится целиком, вместе
  со всеми подчинёнными.
- Объекты из файлов сопоставляются с конфигурацией по полному имени и
  внутреннему идентификатору. Для подчинённых объектов родитель
  определяется по имени файла (линейный формат) или по иерархии каталогов
  (иерархический).
- Формат и расположение подготавливаемых файлов обязаны в точности
  соответствовать файлам выгрузки в выбранном формате.
- **Если при загрузке обнаружены ошибки, происходит возврат к последней
  сохранённой основной конфигурации, а изменённые и несохранённые данные в
  той конфигурации, куда грузили, теряются.** Поэтому перед частичной
  загрузкой в конфигураторе не должно оставаться незаписанной работы.
- Диагностические сообщения частичной загрузки забирает `/Out`.

Условия, при которых она вообще возможна:

- все загружаемые объекты захвачены в хранилище конфигурации;
- для конфигурации на поддержке — у всех загружаемых объектов включена
  возможность изменения;
- при частичной загрузке корневого элемента конфигурация перестаёт
  находиться на поддержке, если отсутствует файл внешнего свойства
  `ParentConfigurations.bin`, хранящий настройки поддержки.

Четыре случая — и ни в одном дело не ограничивается одним файлом
(2.17.5.3.2–2.17.5.3.5):

| Что делаем | Что грузим |
|---|---|
| **Добавление** | сам добавляемый объект **и его родителя** |
| **Удаление** | файл родительского объекта, в котором информации об удаляемом объекте нет |
| **Переименование** | сам объект со всеми подчинёнными **и родителя** со всеми подчинёнными; родитель должен содержать ссылки на объект с новым именем |
| **Изменение** | сам изменённый объект **и все его подчинённые объекты** |

Ошибки, которые руководство называет для добавления: неуникальное имя
загружаемого объекта; ссылка в объекте на подчинённый объект, файлов для
которого не предоставлено. Общее правило для всех четырёх случаев: если
файлов подчинённых объектов нет и ссылок на эти объекты тоже нет, такие
объекты примут значения по умолчанию; если ссылки есть — будет ошибка
загрузки.

Добавление справочника `Контрагенты` в конфигурацию из исходников выглядит
так — два файла, а не один:

```
1cv8 DESIGNER /F d:/base /LoadConfigFromFiles d:/src -files "Configuration.xml,Catalogs/Контрагенты.xml" -Format Hierarchical /DisableStartupDialogs /Out d:/log/partial.txt
```

## Загрузка подчинённых объектов

Загружаемые объекты должны описываться файлами **в точности так же, как при
выгрузке** (2.17.5.3.6). Для линейного формата это значит совпадение имён
файлов, для иерархического — ещё и совпадение иерархии каталогов.

Справочная информация справочника `Товары`:

```
1cv8 DESIGNER /F d:/base /LoadConfigFromFiles d:/src -files "Catalogs/Товары/Ext/Help.xml" -Format Hierarchical /DisableStartupDialogs /Out d:/log/help.txt
```

Структура на диске при этом (иерархический формат):

```
src/
  Catalogs/
    Товары/
      Ext/
        Help.xml
        Help/
          ru.html
          en.html
```

В команде указывается только имя собственно загружаемого объекта — здесь
`Help.xml`. Подчинённые ему файлы (страницы справки по языкам) должны
лежать на диске и будут использованы автоматически.

Модуль объекта справочника `Контрагенты` грузится так же:

```
1cv8 DESIGNER /F d:/base /LoadConfigFromFiles d:/src -files "Catalogs/Контрагенты/Ext/ObjectModule.bsl" -Format Hierarchical /DisableStartupDialogs /Out d:/log/module.txt
```

```
src/
  Catalogs/
    Контрагенты/
      Ext/
        ObjectModule.bsl
```

## Параметры ключа частичной загрузки

Руководство разработчика отсылает за параметрами `/LoadConfigFromFiles` к
книге; их состав — приложение 7 руководства администратора 8.3.27,
раздел 7.4.4:

| Параметр | Что делает |
|---|---|
| `-files "<файлы>"` | какие файлы грузить при частичной загрузке. Список **в кавычках**, файлы **через запятую**, путь полный или относительно каталога загрузки. Несовместим с `-AllExtensions` |
| `-listFile <файл>` | то же списком из файла: по одному имени на строку, кодировка UTF-8, пустые строки не поддерживаются, строка пропускается, если начинается с `REM`. Несовместим с `-AllExtensions` |
| `-Format <режим>` | формат загружаемых файлов: `Plain` — плоский, `Hierarchical` — иерархический (по умолчанию). Используется только вместе с `-files` или `-listFile` |
| `-updateConfigDumpInfo` | создать в каталоге файл версий `ConfigDumpInfo.xml` по итогам загрузки, а при частичной загрузке — обновить существующий |
| `-partial` | грузить только те элементы описания объекта, которые указаны файлом: файл описания объекта метаданных без внешних свойств, файл внешнего свойства (форма и прочее), файл модуля формы без описания самой формы |
| `-NoCheck` | не проверять целостность загружаемой конфигурации; сокращает время, если целостность заведомо известна |
| `-Archive <файл>` | грузить из ZIP-архива; вместе с каталогом загрузки указывать нельзя, нужно одно из двух |

Если в командной строке указаны сразу `-files` и `-listFile`, используется
тот, который стоит первым.

**Расхождение источников, которое надо знать.** Приложение 7 говорит прямо:
при полной загрузке формат (линейный или иерархический) определяется
автоматически, а **для частичной автоматического определения нет и формат
следует указать явно** через `-Format`. Примеры же в §2.17.5.3.6 руководства
разработчика показывают `-files` без `-Format`. Запуском это расхождение не
проверялось; безопасная сторона — указывать `-Format` всегда, лишним он не
будет.

И то, что верно для любой загрузки из файлов: `/LoadConfigFromFiles` меняет
конфигурацию, а не структуру данных базы. Пока не выполнен `/UpdateDBCfg`,
база работает на прежней структуре.
