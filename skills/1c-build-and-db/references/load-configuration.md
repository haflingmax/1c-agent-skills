приложение 7; проверять команды через `scripts/check-1c-cli.py`.

## Что именно грузим

Три разных источника, три разные команды. Их путают чаще всего.

| Источник | Команда | Когда |
|---|---|---|
| Файл поставки `.cf` | `/LoadCfg <файл>` | получена сборка целиком |
| Каталог XML-выгрузки | `/LoadConfigFromFiles <каталог>` | работа велась в исходниках, есть `Configuration.xml` |
| Расширение `.cfe` | `/LoadCfg <файл> -Extension <имя>` | доработка вынесена в расширение |

Загрузка конфигурации **не равна** обновлению базы. `/LoadCfg` меняет конфигурацию, но
структура данных остаётся прежней до `/UpdateDBCfg`. Пока обновление не выполнено, база
работает на старой структуре.

## Шаг 1. Резервная копия — на рабочей базе

**`1cv8.exe` надо явно дожидаться.** Он собран как оконное приложение и возвращает
управление немедленно. Запущенный обычным образом, он не создаст ни файлов, ни журнала,
ни кода возврата — и это выглядит в точности как тихий отказ. В PowerShell:

```powershell
$p = Start-Process -FilePath $exe -ArgumentList $args -Wait -PassThru -NoNewWindow
$p.ExitCode
```

Руководство администратора 8.3.27, раздел 6.7, прямо не рекомендует dt как
резервную копию — безусловно, не только для клиент-серверного варианта.
Решающая причина не в цене: «может возникнуть ситуация, при которой файл
выгрузки будет невозможно загрузить, если в информационной базе… существовали
ошибки» — база с ошибками выгрузится, но не загрузится обратно. Остальные три
причины («длительное время создания», «необходимость монопольного доступа к
базе данных», «высокие требования к оперативной памяти») — цена, а не
негодность.

**Файловая база** (раздел 6.9.1): резервная копия — это копия файла `1Cv8.1CD`,
снятая при полном отсутствии подключений к базе, включая конфигуратор. Не
`1cv8.exe`, а обычное копирование файла:

```powershell
Copy-Item d:/base/1Cv8.1CD d:/backup/1Cv8-2026-08-21.1CD
```

Каталог `d:/backup` должен существовать: команда его не создаёт. К копии
рекомендуется добавить каталог журнала регистрации `1Cv8Log` из каталога
базы — без него резервная копия восстановится, но действия до момента копии
в журнале не найти.

**Клиент-серверная база** (раздел 6.9.2) — резервная копия средствами СУБД,
по шагам: база данных, журнал регистрации, хранилище двоичных данных.

`/DumpIB` в этот шаг не входит: это способ переноса базы между вариантами и
конвертации, а не резервного копирования. Цену он всё равно платит — на
рабочей базе `/DumpIB` требует монопольного доступа безусловно, и
спрашивать об этом надо до запуска, а не после.

На одноразовой базе этого шага нет вовсе: она чинится пересозданием, и вопрос
о копии на ней не рождается.

## Шаг 2. Сохранить то, что заменяем

```
1cv8 DESIGNER /F d:/base /DumpCfg d:/backup/before.cf /DisableStartupDialogs /Out d:/log/dumpcfg.txt
```

Это дешевле полной резервной копии и достаточно, чтобы вернуть конфигурацию, если новая
окажется неверной. Данные при этом не страдают.

## Шаг 3. Освободить базу

Нужно, если обновление будет полным (`-Dynamic-`) и потребует реструктуризации.

**Клиент-серверная.** Блокировка начала сеансов ставится из консоли кластера или через
`ibcmd`; при непустом коде доступа подключение выполняется с `/UC <код>`:

`ibcmd` поставляется с серверными компонентами. Если установлен только клиент,
его в каталоге `bin` не будет, и этот путь недоступен.

```
1cv8 DESIGNER /S srv/base /UC 1234 /LoadCfg d:/new.cf /DisableStartupDialogs /Out d:/log/load.txt
```

Разделитель в `/S` — **прямая косая**: `<сервер>/<имя базы>`. Приложение 7 (7.3.1)
называет три формы и различает их по переносимости: `server-pc/ibName` работает
в любой ОС, `server-pc\ibName` — только в Windows, `"server-pc\ibName"` в кавычках —
снова в любой. Обратная косая без кавычек — единственная форма, ограниченная
одной системой, и по умолчанию она не нужна.

> **Поправка 24.08.2026.** Здесь стояло обратное: «разделитель — обратная косая,
> это единственное место в наборе, где прямая косая неверна». Утверждение
> не подтверждается источником и было исправлено сверкой с приложением 7.

Принудительно завершить сеансы можно самим обновлением:

```
/UpdateDBCfg -SessionTerminate force
```

Значения `<режим>`: `disable` — не завершать принудительно, значение по умолчанию;
`force` — завершать. Завершение сеансов принудительно теряет несохранённую работу
пользователей, поэтому это решение согласуется, а не принимается на месте.

**Файловая.** Достаточно, чтобы никто не держал `1Cv8.1CD`.

## Шаг 4. Загрузка и обновление

Из файла поставки, с полным обновлением:

```
1cv8 DESIGNER /F d:/base /LoadCfg d:/new.cf /UpdateDBCfg -Dynamic- /DisableStartupDialogs /Out d:/log/load.txt /DumpResult d:/log/result.txt
```

Из исходников XML:

```
1cv8 DESIGNER /F d:/base /LoadConfigFromFiles d:/src /UpdateDBCfg -Dynamic- /DisableStartupDialogs /Out d:/log/load.txt /DumpResult d:/log/result.txt
```

Расширение:

```
1cv8 DESIGNER /S "srv\base" /LoadCfg d:/ext.cfe -Extension МоёРасширение /UpdateDBCfg /DisableStartupDialogs /Out d:/log/ext.txt
```

Динамическое обновление — `-Dynamic+`. Оно не требует эксклюзивного доступа, но не проходит
там, где нужна реструктуризация таблиц. Выбор между `-Dynamic+` и `-Dynamic-` делается
заранее и обосновывается, а не подбирается запуском.

## Шаг 5. Проверить результат, а не отчёт

**Отчёт платформы бывает ложным.** Проверено на 8.3.27.2325: команда с выдуманным
ключом `/DumpCfgToFile <путь>\target.cf` вернула `DumpResult` = `0` и записала в
`/Out` «Сохранение конфигурации успешно завершено» — а по указанному пути файл
**не появился**. Это не «ничего не произошло»: платформа опознала в выдуманном ключе
начало настоящего `/DumpCfg`, а хвост `ToFile` разобрала как позиционный аргумент —
имя файла. Конфигурация выгрузилась, только не туда: в файл `ToFile` в текущем
рабочем каталоге, а путь, который передали мы, платформа отбросила как лишний.
Оба отчётных канала не соврали про факт работы — они промолчали про место.

Это опаснее тихого отказа. В рабочем каталоге появляется файл размером с настоящую
выгрузку конфигурации, и на не одноразовой машине он может затереть одноимённый
файл, который там уже лежал.

Поэтому успех определяется по результату — по файлу на *указанном* пути, а не по
факту, что платформа что-то куда-то записала:

| Что делали | Чем доказан успех |
|---|---|
| выгрузка в файл | файл существует, размер больше нуля |
| выгрузка в XML | каталог содержит `Configuration.xml` |
| загрузка конфигурации | **cf того же релиза платформы:** повторная выгрузка побайтно совпадает с загружаемым файлом — сравнение с загружаемым, а не с прежней выгрузкой, работает и при загрузке того же cf. **cf из поставки или другого релиза:** см. оговорку ниже |
| обновление базы | конфигурация базы данных совпала с основной: `/DumpDBCfg` даёт тот же файл, что `/DumpCfg` |

`DumpResult` и `/Out` остаются полезными — но как источник причины отказа,
а не как доказательство успеха.

**Оговорка про побайтное совпадение (проверено запуском 23.08.2026).**
Критерий верен для cf, выгруженного тем же релизом платформы: `/DumpCfg` →
`a.cf` (код 0) → `/LoadCfg a.cf` (код 0, «Загрузка конфигурации успешно
завершена», `DumpResult` = 0) → `/DumpCfg` → `b.cf`; оба файла 75 395 байт,
SHA256 обоих `773C56E8…C88D70F7`. Прогон и его границы —
`docs/evidence/2026-08-23-load-criterion.md`.

Для cf, пришедшего из поставки или собранного **другим** релизом платформы,
побайтное совпадение не обязано получаться, и критерий без этой оговорки
объявлял бы провалом успешную загрузку. Прогон на чужом cf не сделан: на
машине установлен ровно один релиз, 8.3.27.2325, и собрать «чужой» cf нечем.
Чем доказывать загрузку такого файла — открытый вопрос, а не умолчание:
придумывать критерий без прогона здесь запрещено тем же правилом, которым
запрещена блокировка недоказанного.

Пара `/DumpCfg` + `/DumpDBCfg` проверена запуском 22.08.2026 на `D:/1C/base/trade`:
обе выгрузки дали побайтно одинаковый файл (SHA256 совпал), потому что конфигурация
базы данных совпадала с основной. Код возврата 0 был бы получен и при расхождении —
`docs/evidence/2026-08-22-blocking-rules.md`.

Опция `/Out <файл> -NoTruncate` не очищает журнал при новом запуске. В пакетном
режиме запись не буферизуется, поэтому журнал можно читать по ходу длинной операции.

## Что делать, когда не вышло

| Симптом | Причина |
|---|---|
| Команда молча ничего не сделала | нет `/DisableStartupDialogs`: платформа ждёт ответа в диалоге |
| Ошибка про несуществующий каталог | промежуточные каталоги пути не созданы заранее |
| Отказ загрузить расширение | расширение подключено к хранилищу конфигурации; сначала отключить |
| Обновление не проходит динамически | изменение требует реструктуризации, нужен `-Dynamic-` и свободная база |
| Не удаётся подключиться к базе | установлена блокировка соединений, нужен `/UC <код>` |

## Откат

Порядок обратный шагам 1 и 2:

1. вернуть конфигурацию из `before.cf` через `/LoadCfg`, затем `/UpdateDBCfg`;
2. если пострадали данные — восстановить базу целиком: скопировать сохранённый
   `1Cv8.1CD` обратно, при отсутствии подключений (файловая, 6.9.1), либо
   восстановить средствами СУБД (клиент-серверная, 6.9.2). `/RestoreIB`
   годится только тогда, когда резервной копией всё же был dt, а не файл базы.

Второй путь теряет всю работу пользователей с момента копии, поэтому первый пробуется раньше.

## Чего в источниках нет

- **признака, что загруженный `.cf` — тот самый.** Ни контрольной суммы,
  ни подписи файла источник не описывает; порядок проверки здесь построен
  на результате загрузки, а не на файле до неё. То же ограничение у соседа
  `1c-update-and-support` для файлов поставки;
- **машинного признака успеха у части команд:** коды возврата приложение 7
  описывает не для всех ключей, и разбор этого — у соседа `1c-quality-gates`
  (`pipeline-and-return-codes.md`);
- **предварительной оценки, во что обойдётся `/UpdateDBCfg`** — сколько займёт
  реструктуризация и сколько потребуется места, источник заранее не считает;
- **отката загрузки как операции.** Обратной команды нет: откат здесь — это
  восстановление из копии, снятой заранее, и потому шаг 1 стоит первым.
