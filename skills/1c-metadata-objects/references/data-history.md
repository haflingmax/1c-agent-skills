# История данных: версии, которых нет, пока их не обновили

**Ищут по словам:** история данных, версионирование данных, `ИсторияДанных`,
`ОбновитьИсторию`, `ВыбратьВерсии`, `СформироватьПоВерсии`,
`ПолучитьРазличияВерсий`, `ЗаписьИсторииДанных`, очередь версий, очередь
постобработки, `ОбработкаПослеЗаписиВерсийИсторииДанных`, восстановить
версию объекта, кто изменил реквизит.

Источник: руководство разработчика 8.3.27, глава 25 «История данных».
История данных при удалении расширения — у соседа `1c-extensions` (§25.3.10);
удаление истории вместе с областью данных — `data-separation.md`.

**Не путать с версионированием объектов БСП.** В `options-and-session-data.md`
разобрано версионирование из функциональных опций библиотеки — это другой
механизм; здесь платформенный.

**Спина главы: история пишется в два шага, и между ними её нет.** Запись
объекта кладёт изменение в очередь; «настоящей» версия становится только
после переноса из очереди. Всё, что читает историю раньше, видит неполную
картину и не знает об этом.

## Включить свойство мало — нужно регламентное задание

«версия данных становится «настоящей» только после того, как она
перенесена из очереди версий в таблицы хранения истории» (§25.2), а перенос
делает `ИсторияДанных.ОбновитьИсторию()`. Поэтому к свойству объекта
источник сразу добавляет: «После этого необходимо создать регламентное
задание, которое будет выполнять обновление истории данных по очереди
изменений».

**Вывод набора, а не источника:** включённая история без задания копит
очередь и не показывает ни одной версии — пользователь видит «истории нет»,
хотя изменения записаны.

Перед чтением истории конкретного объекта источник советует обновить её
именно для него: «рекомендуется выполнить обновление истории именно
по требуемому объекту с помощью метода ОбновитьИсторию(ЭлементСсылка)»
(§25.3.5) — тогда выборка «будет оперировать полным списком версий».

Ускоренный режим — флажок «Обновлять историю данных сразу после записи»
или свойство `ЗаписьИсторииДанных.ОбновлятьИсториюСразуПослеЗаписи` —
обрабатывает одно изменение одного объекта сразу, но флажок «не
рекомендуется устанавливать для видов метаданных, в которых предполагается
большое количество объектов и будет выполняться интенсивное изменение этих
объектов» (§25.3.3.2).

## Умолчания противоположны: объект выключен, реквизиты включены

«для типообразующих объектов конфигурации ведение истории надо включать
принудительно, а все реквизиты таких объектов автоматически попадают
в историю и необходимо принудительно исключать эти реквизиты из истории»
(§25.2). Измерения регистров сведений в историю попадают всегда, «без
возможности отключения».

**Включение истории у объекта — это сразу все его реквизиты и табличные
части.** Сузить набор надо явно, иначе в историю уходит и то, что хранить
не собирались.

Две особенности устройства, которые меняют смысл правок метаданных:

- «В истории данных не хранятся типы реквизитов, но хранятся только
  фактические значения этих реквизитов»;
- «включение версионирования для реквизита и создание нового реквизита»
  и «отключение версионирования реквизита и удаление реквизита» для
  механизма — одно и то же действие.

И ограничение, о котором узнают при развёртывании: «История данных
не переносится с помощью механизмов распределенной информационной базы»
(§25.1).

## Настройки из кода: неназванное возвращается к конфигуратору

Включать историю можно и кодом — `УстановитьНастройки()`, и это
«не требует снятия конфигурации с поддержки» (§25.2). Но у метода
особенность (§25.3.2): для реквизитов, перечисленных в настройках,
признак ставится, а «Для остальных реквизитов объекта участие
в версионировании будет приведено в соответствие с настройками, указанными
в конфигураторе». Вызов с `Неопределено` сбрасывает всё к конфигурации.

**Вывод набора:** настройки не накапливаются. Второй вызов с другим
списком реквизитов отменяет первый для тех, кого в нём не назвали.

## Постобработка: не удалил из очереди — придёт снова

Обработка после записи версии (§25.3.4) идёт пачками «не более 1 000
версий» в обработчике `ОбработкаПослеЗаписиВерсийИсторииДанных` модуля
менеджера, и обработанное надо убрать самому:

> «В обработчике события ОбработкаПослеЗаписиВерсийИсторииДанных
> необходимо явным образом удалять каждый обработанный объект из очереди
> постобработки. … Если этого не сделать, то версия данных останется
> в очереди постобработки.»

В §25.2 то же сказано жёстче: версия «будет постоянно передаваться
в обработчики событий». А автоочистка идёт по возрасту: «из очереди
постобработки будут удаляться версии данных, созданные более 20 дней назад».

**Вывод набора:** забытое удаление даёт не ошибку, а повторную обработку
тех же версий при каждом обновлении истории — до двадцати дней. Для
обработчика, который меняет цену при смене закупочной (пример источника),
это повторное изменение цены.

## Отбор версий: равенство значения — не факт изменения

`ВыбратьВерсии()` (§25.3.5) требует ровно одно из двух: «Для отбора
необходимо указать или параметр Метаданные, или параметр Данные. Если
указаны оба параметра или оба этих параметра не заполнены ‑ при попытке
получить список версий будет сгенерировано исключение».

Три тонкости отбора:

- **по пользователю** — идентификатор, а не объект `ПользовательИнформационнойБазы`;
  для удалённого пользователя остаются отборы по имени;
- **строка сравнивается по вхождению:** версия подходит, «если значение
  в версии включает в себя значение из отбора»;
- **значение — не изменение.** Источник сам предупреждает после примера
  со скидкой 20 %: «Получившийся список не есть список версий, в которых
  значение реквизита было изменено!» Чтобы найти версии, где скидка
  **стала** 20, нужен элемент `ЗначениеПослеИзменения` в `ЗначенияПолей`;
  и «Отбор позволяет указывать проверки только по условию равенства двух
  значений. Другие виды условий не поддерживаются».

## Восстановление версии регистра перезаписывает весь набор

`СформироватьПоВерсии()` возвращает объект версии, который можно записать
заново (§25.3.6). Для подчинённого регистра сведений это опасно:

> «Сформированный набор записей содержит все строки набора записи, которые
> могут быть получены из базы данных по указанному ключу. Следовательно,
> при записи такого набора записей будут обновлены все записи набора,
> а не только одна запись, которая восстанавливается из истории. Это
> означает, что в том случае, когда между получением данных версии
> и записью этих данных произойдет изменение прочитанных данных из другого
> сеанса, то данные, внесенные из другого сеанса, будут утеряны.»

Средство источник называет одно: «необходимо накладывать блокировки
на изменяемые данные».

Версия удаления объекта тоже восстановима: будет получен объект,
«заполненный данными, которые были в объекте в момент удаления».

## Разница версий смотрит глазами поздней

`ПолучитьРазличияВерсий()` (§25.3.9) не вычисляет изменения, а отдаёт
значения двух версий, и опирается «на структуру метаданных, которая была
в момент формирования версии после изменения». Отсюда:

- реквизит, удалённый между версиями, из разницы **пропадает** — «разница
  между версиями не будет содержать никакой информации по удаленному
  реквизиту»;
- у появившегося реквизита источник противоречит сам себе: сначала «в качестве
  значения до изменения будет выступать значение по умолчанию для
  соответствующего типа», двумя абзацами ниже — «элемент структуры с ключом
  ЗначениеДоИзменения будет отсутствовать». Код, разбирающий разницу,
  проверяет наличие ключа, а не только значение;
- «При сравнении версий не производится попытки приведения типов» —
  смена типа даёт различие даже при равном значении;
- перемещение строки табличной части «никак не отражается в списке полей».

Комментарий версии — не длиннее 1024 символов (§25.3.7).

## Опечатки источника, на которые не надо ловиться

Одно свойство `ЗаписьИсторииДанных` названо в главе тремя способами:
`ВыполнятьОбработкуПослеЗаписи` (§25.2), `ВыполнятьОбработкуПослеЗаписиВерсии`
и `ВыполнитьОбработкуПослеЗаписиВерсии` (§25.3.3.1, §25.3.4); метод
представления допданных — `ДобавитьПредставлениеПоляДополнительныхДанных()`
и `ДобавитьПредставлениеДополнительныхДанных()`; выборка один раз названа
`ВыборВерсий()`. Точное имя сверяют с синтакс-помощником.

## Чего в главе 25 нет

- **объёмов:** сколько места занимает история и как она растёт, глава
  не говорит; есть только совет по частоте регламентного задания
  «определяется количеством версионируемых объектов, интенсивностью
  их изменения»;
- **правил, что версионировать.** Выбор между конфигуратором и кодом
  описан, критерия «какие объекты нужны в истории» нет. В системе
  стандартов слов «история данных» нет ни разу; «версионирование»
  встречается только примером функциональной опции в `std470`;
- **признака переполненной очереди** версий или постобработки.
