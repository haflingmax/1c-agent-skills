# Стандартный интерфейс OData

**Ищут по словам:** OData, `standard.odata`, `$filter`, `$top`, `$skip`,
`$select`, `$expand`, `allowedOnly`, префикс имени ресурса, `RowType`,
`RecordType`, `like`, `substringof`, `dateadd`, коды ошибок OData,
публикация OData.

Источник: руководство разработчика, глава 17, §17.4.

Правило про закрытый список типов объектов стоит **в теле навыка**; здесь
остальное.

## Имя ресурса собирается по правилу (§17.4.4)

«При обращении к какому-либо ресурсу, его идентификатор формируется
по следующему принципу: **ПрефиксИмени_ИмяОбъектаКонфигурации_СуффиксИмени**».

Имя берётся ровно из конфигуратора: «ИмяОбъектаКонфигурации ‑ свойство Имя
объекта конфигурации, как оно задано при разработке прикладного решения
в конфигураторе».

Отсюда прямое следствие для интеграции: **переименование объекта метаданных
меняет публичный адрес ресурса**. Потребитель OData ходит по имени, которое
для вас внутреннее.

**Префиксов четырнадцать**, и список закрыт: `Catalog`, `Document`,
`DocumentJournal`, `Constant`, `ExchangePlan`, `ChartOfAccounts`,
`ChartOfCalculationTypes`, `ChartOfCharacteristicTypes`,
`InformationRegister`, `AccumulationRegister`, `CalculationRegister`,
`AccountingRegister`, `BusinessProcess`, `Task`.

В нём нет перечислений, отчётов, обработок, общих модулей и ролей. Прямого
«эти типы недоступны» источник не пишет — это следует только из закрытости
таблицы, и это разница между «не нашёл» и «нельзя».

**Суффиксы** — тоже закрытый список: имя табличной части, имя реквизита
табличной части или набора записей, имя виртуальной таблицы регистра,
`RowType`, `RecordType`.

Виртуальная таблица приходит функцией: «Имя функции совпадает с английским
вариантом имени используемой виртуальной таблицы языка запросов».

## Заголовок §17.4.5 шире своего содержания

«Правила формирования условия отбора» накрывают четыре разнородных
параметра, и три из них к условию отбора отношения не имеют: `$top` —
ограничение количества, `allowedOnly` — переключатель прав, `$skip` —
постраничный пропуск. Условие отбора — только `$filter`.

## `$filter`: часть функций протокола не работает, одна работает иначе

Операции закрытыми списками: логические `eq`, `ne`, `gt`, `ge`, `lt`, `le`,
`or`, `and`, `not`; арифметические `add`, `sub`, `mul`, `div`; скобки для
приоритета. «Операции с одинаковым приоритетом вычисляются слева направо».

**Часть стандартных функций протокола не поддерживается вовсе**, и список
закрыт: «Не поддерживаются следующие стандартные функции: **lenght, indexof,
replace, tolower, toupper, trim, years, days, hours, seconds, floor,
ceiling**». Опечатка «lenght» — из источника.

**А одна поддерживается, но по-своему:** `like(Str, Template)` — «Возвращает
true, если значение Str1 удовлетворяет шаблону Template. **Синтаксис шаблона
аналогичен функции ПОДОБНО() языка запросов**».

То есть шаблон здесь не стандартный для OData, а 1С-овский. Что происходит,
если потребитель пишет по спецификации протокола, источник не говорит.

**Даты работают с закрытым набором единиц:** «second ‑ секунды; minute ‑
минуты; hour ‑ часы; day ‑ дни; month ‑ месяцы; quarter ‑ кварталы; year ‑
года». Ни недели, ни декады в нём нет.

## `allowedOnly`: ошибка не гарантирована ни в ту, ни в другую сторону

«Если при выполнении запроса необходимо получить только те объекты данных,
которые не попадают под ограничения доступа к данным, то в URL получения
данных **необходимо добавить параметр allowedOnly**».

А без него: «Если параметр не указан или указан со значением false,
то во время исполнения запроса к данным **может возникнуть ошибка с кодом
401**… **Ошибка может не произойти** в том случае, если были указаны
дополнительные условия, которые ограничили выборку только разрешенными
данными».

Двойное «может» — не расплывчатость источника, а описание механики: 401
зависит от того, попали ли запрещённые данные именно в эту выборку.
Один и тот же запрос на разных данных ведёт себя по-разному, и тест
на «своих» данных этого не покажет.

## Расхождение заголовка ещё в одном месте

**§17.4.9 «Выполнение функций и действий»** описывает только функции;
пример действия (проведение и отмена проведения документа) лежит
в §17.4.13.1.7 под совсем другим заголовком. Искать «действия» по номеру
параграфа бесполезно.

## Чего в §17.4 нет

- **под чьей учётной записью выполняется OData-запрос** — §17.4 не говорит,
  и схем аутентификации для OData здесь не названо ни одной, в отличие
  от web-сервисов. Но ответ есть в другой книге: порядок общий для всего,
  что идёт через расширение веб-сервера, и расписан в руководстве
  администратора, §4.3.8.2.3 (разобран в `http-services.md`). Про права
  §17.4 даёт только результат их проверки: код ошибки 20 в таблице кодов
  и параметр `allowedOnly`;
- **явного «остальные типы недоступны»** — только закрытая таблица
  префиксов;
- **цена массовой выгрузки** — производительность и объёмы глава
  не обсуждает, хотя §17.4.1 называет загрузку и выгрузку типовой задачей.
  Сам механизм массовой выгрузки при этом есть: §17.4.13.3 даёт `SelectChanges`
  и `NotifyChangesReceived` — тот же протокол сообщений плана обмена, только
  транспортом OData.

## Запись через OData: четыре операции и их несимметричность (§17.4.13.1)

Чтение через OData выглядит безобидно, запись — нет. Различия между методами
здесь не косметические.

**Создание** — POST на канонический URL сущности с телом в atom или json.

**Обновление — два метода с разным смыслом** (§17.4.13.1.3): «В случае
**PATCH**-запроса пропущенные свойства сущности **будут проигнорированы**,
т. е. будут изменены только те свойства, которые переданы в запросе
на изменение. Для **PUT**-запроса **необходимо указывать значения всех
свойств** обновляемой сущности».

То есть `PUT` с половиной полей — не «частичное обновление», а обновление
всей сущности, где недосланное берётся не из базы.

Обе операции молча глотают лишнее: «Если передаваемый документ содержит
свойства, отсутствующие у создаваемого объекта, то **эти свойства
игнорируются**». Опечатка в имени поля не даст ошибки — она просто не
запишется.

Фраза приведена по §17.4.13.1.3 «Обновление объекта», где источник повторяет
её дословно из §17.4.13.1.2 «Создание объекта» — вместе со словом
«создаваемого», хотя речь об обновляемом. Слово чужое, но правило то же.

**Ссылки пишутся особым полем** (§17.4.13.1.3): «При модификации сущности
через PUT-запрос, при записи значений ссылочных реквизитов, **следует
использовать поле ИмяСсылочногоРеквизита@odata.bind** куда следует поместить
URI-сущности (можно в укороченном варианте ‑ только фрагмент пути после
standard.odata)».

**Удаление** — правило стоит в теле: «Внимание! **Пометка на удаление
не выполняется, объект удаляется непосредственно**» (§17.4.13.1.4).

**И единственная защита от гонки — необязательная** (§17.4.13.1.5):
«Для оптимистической блокировки данных (т. е. для проверки, что данные
не изменились с момента считывания) **нужно использовать заголовок If-Match**
HTTP-запроса, связанного с модификацией (PATCH) или удалением (DELETE)
данных. В качестве значения заголовка **должно выступать значение свойства
DataVersion**, которое получено при предварительном чтении сущности».

Не прислали `If-Match` — записали поверх чужой правки, и никто не сообщит.

## Выгрузка изменений через OData (§17.4.13.3)

Тот же протокол сообщений плана обмена, что описан для XML и веб-сервисов,
имеет и OData-транспорт: `SelectChanges` отдаёт зарегистрированные изменения,
`NotifyChangesReceived` подтверждает приём.

Значит, узел обмена может быть не только базой 1С, но и внешней системой,
которая ходит по HTTP, — а правила регистрации, номеров сообщений
и подтверждения остаются теми же (см. `exchange-plans-and-registration.md`).
